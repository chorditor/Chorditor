## 1. 방향과 챕터 공통 틀

- 9개 챕터를 여러 레벨로 세분화한다(레벨 수 대폭 증가). 기존 3단 난이도(쉬움·보통·어려움)는 폐기. 문제 유형을 늘리고 UI 레이아웃을 바꾼다.
- 훈련소는 '나의 기타 여정'을 보조하는 챌린지 성격이므로 커리큘럼을 지나치게 무겁게 하지 않는다.
- **챕터 공통 틀(챕터 1 방식)**: ① 챕터 시작은 미니강의 → ② 강의를 들으면 필수 레벨 구간이 한꺼번에 열림 → ③ 필수 구간의 마지막이 키 레벨(클리어 5회), 클리어하면 선택 레벨 구간의 첫 레벨과 다음 챕터(미니강의 포함)가 열림 → ④ 선택 레벨은 키 레벨 클리어 전까지 잠금 UI이고 열린 뒤에도 한 레벨씩 클리어해야 다음이 열림 → ⑤ 레벨 수·선택 구간 길이는 챕터별로 다를 수 있음.

### 챕터별 학습목표 (9개 챕터, 2026-10-26)

**챕터 1 — 다이어토닉 코드**
- M과 m 코드의 원리를 이해한다.
- 여러 key의 다이어토닉 코드의 도수를 암기하고, 순서대로 배치할 줄 안다.

**챕터 2 — 코드의 기능**
- 다이어토닉 코드를 7th로 확장할 줄 안다.
- 다이어토닉 코드를 기능에 맞게 분류할 줄 안다.
- 같은 기능 안에서의 대리코드 개념을 알고 적용할 줄 안다.

**챕터 3 — 코드 꾸미기**
- add9, sus2, sus4 같은 대중음악에서 주로 쓰는 텐션을 넣어 코드를 꾸밀 줄 안다.
- 전위코드로 대리코드를 적용하고 베이스라인을 부드럽게 만드는 것을 이해한다.

**챕터 4 — 세컨더리 도미넌트**
- 특정 음이 제시될 때 그 음의 5도 위 음을 찾을 수 있다.
- 다이어토닉 코드에서 타겟 코드의 세컨더리 도미넌트 코드를 찾고 적용할 줄 안다.

**챕터 5 — 릴레이티드 투-마이너**
- 타겟 음을 1도로 하는 2-5-1 진행을 찾고 적용할 수 있다.
- 논다이어토닉 코드를 구분하고, 릴레이티드 투파이브원이 어디에 쓰였는지 찾을 수 있다.

**챕터 6 — 도미넌트의 대리코드**
- 도미넌트가 3도 위의 dim7 코드로 대리됨을 이해하고 적용할 수 있다.
- 도미넌트의 트라이톤을 공유하는 또 다른 대리도미넌트 코드의 생성 원리를 이해하고 코드진행에 적용할 수 있다.

**챕터 7 — 텐션코드**
- 다이어토닉 코드에서 쓸 수 있는 정석적인 텐션을 분류하고 교체할 수 있다.

**챕터 8 — 마이너 다이어토닉**
- 마이너 스케일을 이용한 다이어토닉 코드가 존재함을 이해하고, 마이너 다이어토닉 코드 진행과 도수를 파악할 줄 안다.

**챕터 9 — 모달 인터체인지**
- 나란한조의 개념을 이해하고, 다른 key의 다이어토닉 코드를 잠시 빌려오는 모달 인터체인지를 이해한다.
- 자주 쓰이는 몇 가지 모달 인터체인지 코드를 다양한 key에서 적용할 줄 안다.

## 2. 챕터·레벨 구성

### 공통 레벨 구조 (챕터 3~7·9, 챕터 4·5·7·9는 2026-10-26 확정)

| 번호 | 내용 | 구간 |
|---|---|---|
| N-1 ~ N-5 | C, G, D, A, E key 각각(한 레벨 한 key) | 필수(미니강의 후 열림) |
| N-6 | 5key 종합(C G D A E) — **키 레벨** | 필수 |
| N-7 ~ N-13 | F, Bb, B, Db, Eb, Gb, Ab key 각각 | 선택(N-6 클리어 후 열림) |
| N-14 | 12key 챌린지(제목은 임시안) | 선택 |

### 현재 열림/잠김 (2026-10-28 — 순차 해금 시스템)
- 마크업의 열림/잠김은 **초기 상태일 뿐**, 페이지 로드 때 `_comboV2RenderProgress()`가 저장된 진행대로 다시 그린다(§4 "레벨 진행·순차 해금"). 신규 유저는 **1-1만 열림**.
- 모든 레벨 카드는 `data-level="N-M"`이 있어야 한다(카드 128장 = `COMBO_V2_LEVELS` 128개 일치 확인). 챕터별 필수 구간 마지막(키 레벨) 번호는 `COMBO_V2_REQ`(챕터 2만 2-8, 나머지 N-6).
- 선택 구간 안내 문구("N-6을 클리어한 후 도전해요")는 열린 뒤에도 남는다(정리 필요, §9).

## 3. 문제 유형과 레벨 설정값

| 유형 | 문제 | 유저 행동 | 제출 후 | 사용처 |
|---|---|---|---|---|
| 연결형 | 섞인 코드 3~4개 + 도수 | 짝 카드를 터치해서 매칭 | 정답 표시만 하고 바로 다음 | 챕터 1~6·8·9 |
| 배치형 | 도수 진행(항상 표시) + 진행 사운드 | 하단 코드풀을 터치해 칸을 채움(길게 눌러 드래그로 이동·교환 가능) | 완성 진행 재생 후 다음 | 전반 |
| 교체형 | 교체 전 진행 + 사운드, 타겟 칸 표시 | 하단 코드풀에서 터치해 타겟 칸만 교체 | 교체된 진행 재생 후 다음 | 전반 |
| 분류형 | 하단에 다이어토닉 코드 7장(실제 코드명) | 해결·예비·긴장 3개 열에 나눠 담기 (스파이더 카드 게임처럼) | 전부 맞아야 정답(칩이 맞는 열에 있으면 연두) | 챕터 2·3(전위 테마)·8 |

- 연결형 목적은 암기: "C key에서 IV도는 F" 같은 도수↔코드명 매칭. 터치 조작이 기본.
- 배치형·교체형·빈칸형: 도수 힌트는 항상 보여 준다(청음 훈련이 아니므로). **사운드는 안내 카드 좌상단 스피커로 정답 진행을 들려준다(§8)**. 진입 시 자동 재생은 하지 않음. 분류형·연결형에는 소리가 없다.
- 분류형 정답 분포(챕터 2): 해결 3(I·IIIm·VIm), 예비 2(IV·IIm), 긴장 2(V·VIIdim). 챕터 3 전위 테마는 10개, 챕터 8 마이너는 8개(7-2, 7-7).
- **레벨 설정값** `COMBO_V2_LEVELS['N-M']`: key 풀 / 유형 목록(`kinds`) / 챕터 플래그(`seventh` `func` `ch3`~`ch9` `challenge`). 레벨 추가 = 이 표에 값만 추가(+ 카드에 `data-level`). 한 레벨 안에서 유형을 섞고, 유형별 비율은 챕터마다 §7에 정리.

- **같은 문제**: 문제를 만들 때 쓰는 난수를 문제별 시드(`_comboV2WithSeed`, mulberry32)로 고정하고, 만들기 직전 세션 상태(prevKey·prevId·used)와 함께 `s.snaps[idx]`에 저장한다. 오답풀이는 그 시드·상태로 같은 빌더를 다시 돌려 칩·선택지 순서까지 똑같이 재현한다. 전 레벨(1-1~9-14)에서 원본과 재현본의 DOM 쓰기 기록·상태를 비교한 결과 일치(20,400건 + 이전 34,000건, 불일치 0), 시드를 바꾼 대조군은 거의 전부 불일치(검증이 실제로 차이를 잡음).
- **맞힐 때까지 재도전**: 오답풀이에서 틀리면 다음으로 안 넘어가고 버튼이 "다시 풀기"가 된다. 틀린 부분만 비운 뒤 다시 푼다 — 연결형 = 틀린 짝만 풀리고 **표시는 없음**(맞힌 짝은 유지·잠김), 배치형 = 틀린 칩은 그 자리에 남고 **칩 배경만 연한 오답색**(`#F9CFCC`, 테두리 없음 — 옮기거나 빼면 표시가 사라짐), 교체형·빈칸형 = 틀린 선택지가 연한 오답색이 되고 다시 못 고름(정답 도수 힌트도 원래대로 되돌림), 분류형 = 틀린 칩이 풀로 돌아가며 연한 오답색. 선택지가 줄거나 틀린 부분만 비워지므로 반드시 정답에 도달한다.
- 화면: 문제 타이틀 아래에 작은 `오답풀기` 배지(`.combo-v2-review-badge`, 챕터 포인트색). **진행 막대(탑바 게이지)는 본 문제와 오답풀이를 통틀어 하나**이고, 맞든 틀리든 풀면 한 칸 진행하되 틀릴 때마다 전체(분모)가 하나씩 늘어난다(10문제 중 3개 틀리면 본 문제를 마친 시점 10/13 ≈ √ 곡선 88%) — 오답까지 전부 풀어야 100%. 곡선·색 전환 임계값은 행동심리학 장치라 바꾸지 않는다(style-guide §21).
- **안내 화면**(오답풀이 직전, 자동 진행): 레이아웃은 두 묶음 — **윗묶음**(피크 아이콘 + "오답을 풀면 피크 N개를 돌려받아요")은 시선이 몰리는 화면 위쪽 절반(높이 52% 영역의 가운데), **아랫묶음**(완주 조건·재도전 보충 설명)은 그 바로 아래 중하단에 간격을 두고 나눠서 보인다(화면 맨 아래는 비움). 등장 순서: 피크 아이콘이 크게 팝인 → "오답을 풀면 피크 N개를 돌려받아요"(N = 아직 못 받은 환급) → "끝까지 완주해야 레벨 클리어예요" → "틀려도 맞힐 때까지 다시 도전할 수 있어서 부담 없어요!" 순으로 하나씩 뜨고(앞 요소 `animationend` 뒤), 요소마다 0.9초에 걸쳐 떠오르고 앞 요소가 끝난 뒤 0.9초 쉬었다 다음 요소가 뜨며(`COMBO_V2_INTRO_GAP_MS`, 읽을 시간 확보), 마지막 줄 뒤 2초 머물다 오버레이가 걷히며 틀린 첫 문제가 드러난다. Pro는 피크가 없어 환급 문구·아이콘을 생략한다. 피크 개수 강조색(안내 문구의 숫자·환급 "+1")은 빨강이 아니라 노랑(`--icon-yellow`)으로 통일. 탭 건너뛰기는 두지 않음. 글자는 빨리 읽히도록 줄 문구 18px 이상(`--font-title`, 481px~ 18/20px), 제목 24px 이상(`--font-headline-sm`). 줄 문구 색도 회색이 아니라 `--text-primary`(진하게).

**레벨 완료·클리어 (2026-10-22 변경)**
- '완료' 1회 = 오답풀이까지 진행해서 모든 문제를 맞히고 끝까지 마쳤을 때(오답풀이는 맞힐 때까지 반복이라 끝까지 하면 전부 맞힌 상태). '클리어' = 완료 3회(**키 레벨, 즉 챕터 필수 구간 마지막 종합 레벨은 완료 5회**). 도중에 나가면 그 회차는 완료로 세지 않는다.
- **완주 화면**(2026-10-28; 코드·CSS 이름은 `clear`): 푼 결과가 아니라 완주 축하·칭찬. 읽히는 묶음은 정중앙이 아니라 화면 위쪽 절반(아래 22%를 비워 위로 올림)에 둔다(style-guide §22). 트로피 팝인 + 색종이 + 효과음 `reward.mp3`(앱 공용 보상음, `_playSfx`) → **"완주!"**(완료 1회를 마칠 때마다. 도넛 호를 마지막까지 채운 판 — 일반 레벨 3번째·키 레벨 5번째 — 에서만 **"레벨 클리어!"**로 구분. "클리어"는 레벨이 열리는 사건을 뜻하므로 평소 판에 쓰면 다음 레벨이 열린 것으로 오해할 수 있음) → 레벨 이름 → 칭찬 문구(오답풀이를 했으면 "틀린 문제도 끝까지 풀어냈어요…", 아니면 "한 문제도 안 틀렸어요…") → 하단에 붙은 텍스트 버튼 "돌아가기"(누르면 문제 화면과 함께 오른쪽으로 슬라이드되며 선택 화면). 레벨·칭찬 문구는 진한 색 16px(`--font-title-sm`)이고 '레벨 클리어!'와는 32px 더 띄운다. 환급 안내는 카드 없이 칭찬 문구 아래 **한 줄 "피크 N개를 돌려받았어요"**(앞에 피크 아이콘, N = 문제 수 ÷ 5, 개수는 노랑 강조)로 **항상** 표시한다(완벽 클리어든 오답풀이를 했든 최종 환급량을 확인). Pro는 생략. 클리어 화면에서 X는 확인 모달 없이 바로 나간다. 완료 횟수 기록·잠금 연동은 아직 안 붙임(§9).

**피크 정산 (2026-10-28)**
- 진입 비용 = 환급 총합 + 2: **10문제 레벨 4개 / 15문제 레벨 5개**(`_comboV2PeakCost`). 정답이 **누적 5개 쌓일 때마다 즉시 1개 환급**(오답풀이에서 맞힌 것도 포함) → 전부 맞히면 10문제 2개, 15문제 3개가 돌아와 **순소모 항상 2개**. 중간에 나가면 이미 받은 환급은 유지하고 남은 환급은 받지 못한다(나가기 모달에 안내). Pro는 소모·환급 없음.
- 환급 연출: 탑바 피크 개수가 통통 튀고 아래로 "+1"이 떠올랐다 사라진다. 상수 `COMBO_V2_REFUND_EVERY`, `COMBO_V2_PEAK_NET`.
- **서버 반영은 일괄 전송**: 정답 5개마다 서버를 부르지 않는다. 화면 숫자만 즉시 올리고(표시 = 서버 잔액 + 환급 대기분, `addPendingRefund`), 대기분은 localStorage(`chorditor_peak_refund_pending`)에 쌓아 두었다가 **훈련을 나갈 때(X 확인·클리어 확인) / 클리어 화면 진입 때 / 이탈(pagehide·백그라운드) 때 / 앱이 꺼졌다면 다음 로드 때**(`refreshPeakState`, 훈련 중이 아닐 때) `flushPendingRefund`가 서버 RPC `refund_peak(p_amount)`로 한 번에 보낸다. 전송은 멱등(전송 중 중복 호출 무시, 성공한 만큼만 대기분에서 뺌)이고, 로그인 상태에서 RPC가 실패하면 대기분을 남겨 다음에 다시 보낸다(로컬 성공 처리·유령 잔액 없음). 비로그인은 로컬 폴백, DEV는 소모를 안 하므로 서버·저장 없이 화면 잔액만 올린다. Pro는 대기분을 쌓지 않는다.
- **서버 RPC는 아직 없음(SQL 승인 후 작성 예정)**: `refund_peak(p_amount integer)` — 회복 반영 후 `p_amount`(1 이상)만큼 잔액에 더하고 `ok`·`balance`·`peakbox_count`를 JSON으로 반환(`grant_peak_ad.sql` 패턴). 일괄 전송이라 한 번에 3개를 넘을 수 있어 상한을 두지 않는다. 배포 전에는 로그인 계정의 대기분이 서버에 안 쌓이고 계속 남는다. 하루 한도 같은 추가 제한은 두지 않기로 함(훈련할 권리를 줄이지 않는다).
- **리하모니 화성학 전용 탑바**: 선물상자(피크상자)를 빼고 피크 개수(`28/30`)만 표시. 퀴즈 중에도 진행 막대 오른쪽에 계속 보인다(이전엔 퀴즈 중 숨겼음).
- 레벨 카드에 완료 횟수(0~3)를 도넛 호 3개로 표시하고 백엔드에도 저장한다(§5).

**레벨 진행·순차 해금 (2026-10-28, 구현됨)**
- **완료 횟수(도넛 호)**: 레벨을 끝까지(오답풀이 포함) 마치면 클리어 화면에 들어가는 순간 완료 1회가 기록된다(`comboV2RecordClear`, 최대 3회). 도넛의 호 `i < 완료 횟수`가 챕터 색으로 켜지고 `aria-label`은 `N/3`. 3회 = **클리어**. 단 **키 레벨(N-6, 챕터 2는 2-8)은 5회가 클리어**이고 도넛 호도 5개(`combo-v2-donut--5`, 둘레를 5칸으로 나눔, 틈 6px 동일; `_comboV2ClearAt`·`COMBO_V2_CLEAR_AT_KEY`).
- **해금 규칙**(`_comboV2LevelOpen`, 2026-10-28): 챕터 안의 **모든 레벨(필수·선택 구간 모두)은 바로 앞 레벨을 클리어해야 다음이 열린다** — 일반 레벨 3회·키 레벨 5회. 선택 구간 첫 레벨(N-7)은 키 레벨 클리어 후, 이후 N-8 ~ 마지막(12key 챌린지)까지 한 단계씩. 챕터 N의 첫 레벨은 이전 챕터 키 레벨 클리어 후(1장은 항상). 챕터 설계의 "미니강의 후 필수 구간이 한꺼번에 열림"·"키 레벨 클리어 후 선택 구간이 한꺼번에 열림"을 **레벨 하나씩 클리어하는 방식으로 바꿨다**(3회 클리어의 의미를 살리고 성취감). 신규 유저는 1-1만 열린 상태. **해금 판정 구조(2026-10-28 재설계, `_comboV2KeyPassed` / `_comboV2ChapterOpen` / `_comboV2LevelOpen` / `_comboV2MaxChapter`)**: 저장하는 사실은 `done`(레벨별 직접 완주 횟수 — 퀘스트·보상은 이것만)과 `skips`(통과한 건너뛰기 대상 챕터, 판정엔 최댓값 S)뿐이고 해금 상태는 따로 저장하지 않고 매번 계산한다. `keyPassed(c)` = 챕터 c 또는 **더 높은 챕터**의 종합 레벨 클리어, 또는 c < S → `chapterOpen(n)` = n=1 또는 `keyPassed(n-1)` → `levelOpen(c,m)` = 챕터가 열려 있고 [첫 레벨 항상 / 필수 구간 = 앞 레벨 클리어 또는 `keyPassed(c)` / 선택 구간 첫 레벨 = `keyPassed(c)` / 선택 구간 나머지 = 앞 레벨 클리어]. 원칙: 건너뛰기로 챕터 S에 들어갈 자격을 얻었다면 S보다 낮은 챕터의 관문도 모두 통과한 것으로 본다(해금만, 클리어 기록 아님). 예: 5장으로 건너뛰면 1-7·2-9·3-7·4-7과 5-1이 열린다(3-7 같은 낮은 챕터의 선택 첫 레벨이 안 열리던 문제를 이 구조로 해결).
- **지난·건너뛴 챕터**: 열린 가장 높은 챕터(`_comboV2MaxChapter` = `max`(직전 챕터 키 레벨이 클리어된 가장 높은 챕터, 건너뛰기로 통과한 챕터 목록 `_skips`의 최댓값))보다 낮은 챕터는 **필수 구간(종합 레벨 포함)이 전부 열려 있다**(클리어는 아님). 그 챕터의 선택 구간은 키 레벨을 직접 클리어해야 열린다(단 건너뛰기 테스트가 종합 역할을 한 직전 챕터는 선택 구간 첫 레벨이 열림). 해금(`_skips`)과 클리어(완료 횟수)는 별개의 데이터다.
- **접속 시 위치(2026-10-28)**: 선택 화면을 열 때 **열린 가장 높은 챕터 카드가 스티키 헤드 바로 아래에 오도록 애니메이션 없이 스크롤**하고 챕터 점도 그 챕터로 둔다(1장이면 그대로). 서버 병합으로 열린 챕터가 바뀌어도 유저가 아직 스크롤하지 않았을 때만 다시 맞춘다. 레벨을 풀고 돌아올 때는 보던 위치 유지.
- **채움 연출(2026-10-28)**: 클리어 화면에서 "돌아가기"로 선택 화면에 돌아와 슬라이드가 끝나면(`transitionend`), 방금 채워진 도넛 호가 **`cubic-bezier(0.25, 1, 0.5, 1)`(easeOutQuart) 600ms**로 시계 방향으로 그려진다(회색 호 위에 같은 모양의 챕터색 복제 호를 `stroke-dasharray` 0.01 → 호 길이로 키움). 기록은 클리어 화면 진입 때 저장되지만 화면(호·다음 레벨 해금)은 연출이 끝난 뒤에 반영된다. 호가 다 채워진 **직후 도넛(안의 레벨 번호 포함)이 1.18배까지 커졌다 돌아오는** 효과(400ms, ease-in-out)가 붙는다(레벨 제목은 커지지 않음). 다른 레벨에 들어가거나 이탈하면 연출을 취소하고(커지는 효과 없이) 실제 상태를 바로 그린다.
- **챕터 카드 위쪽 여백(2026-10-28)**: 두 번째 챕터부터 챕터 카드 위에 `--space-10`(40px)을 더해 앞 챕터의 레벨 카드와의 간격을 리스트 gap 12px + 40px = **52px**로 넓혔다(다른 묶음으로 보이게). 첫 챕터는 헤드 간격(`--cd-head-gap`)이 있어 제외.
- **서버 동기화(2026-10-28, 클라이언트 구현됨 / 서버 SQL은 `supabase/combo_progress.sql` 작성 완료, **DB 반영은 아직 안 함(앱 배포 전에 `refund_peak.sql`과 함께 한꺼번에)**)**: 진행도는 DB가 기준, 로컬(localStorage)은 캐시. 로그인 상태에서만 동기화하고 비로그인은 로컬만. 기록은 **로컬에 먼저 반영하고 대기열**(`chorditor_combo_sync_q_v1_<uid>`)에 쌓아 순서대로 서버로 보내며, 실패(네트워크·미배포)해도 대기열이 남아 다음 접속·다음 기록 때 다시 보낸다. 접속 시 `comboV2SyncPull`: 대기열을 비우고 → `get_combo_progress`로 받은 값을 **큰 값 기준(GREATEST)으로 병합**(로컬 값을 서버에 덮어쓰지 않음, 서버 값은 상한 3/5로 제한) → 로컬에만 있는 진행분(완료 횟수·건너뛰기 챕터)은 한 번 서버로 올림(기존 로컬 진행 이전). 대기열이 남아 있으면 병합을 건너뛴다(중복 방지).
  - **RPC 규약**(모두 `auth.uid()` 기준): `get_combo_progress()` → `{ok, levels:{"1-1":n,…}, skips:[3,5]}` / `record_combo_level(p_level text)` → `{ok, done, cleared, first_clear}` (완료 횟수 +1, 키 레벨 5·일반 3에서 멈춤, **`first_clear` = 이번에 처음 클리어에 도달**하면 true — 퀘스트·보상 판정은 이 값과 처음 클리어한 시각만 보면 되고 같은 레벨로 보상을 두 번 받는 것도 막힘) / `record_combo_skip(p_chapter int)` → `{ok, skips:[…]}` (통과한 건너뛰기 대상 챕터를 집합에 추가, 멱등, 완료 횟수·퀘스트와 무관). 키 레벨 표(N-6, 챕터 2만 2-8)는 서버 SQL에도 같이 둔다(서버가 클리어 판정).
  - **테이블(추가만, 기존 변경 없음)**: 레벨 진행(user_id, level, done, first_cleared_at, updated_at; PK user_id+level) / 건너뛰기 통과(user_id, chapter, passed_at; PK user_id+chapter — 행 하나 = 통과한 대상 챕터). RLS는 본인 행만. 앱보다 SQL을 먼저 반영.
- **챕터 미니강의 잠김 + 건너뛰기 테스트(2026-10-28, 구현됨)**: 챕터가 열리기 전(그 챕터 첫 레벨이 잠겨 있을 때 = 이전 챕터 키 레벨 미클리어)에는 챕터 카드의 재생 버튼이 자물쇠 + 회색이 되고, 그 칸 윗줄("N장" 라벨과 같은 높이)에 **"건너뛰기"** 글자가 붙는다. 챕터 1은 항상 열림. **잠긴 챕터 카드 전체(2~9장 모두)를 누르면 건너뛰기 테스트**가 시작된다→ **모달이 아니라 전체 화면을 덮는 안내 페이지**(`#combo-v2-skip-page`, body 직속 fixed)가 뜬다: 위쪽 영역에 한 줄 "건너뛰기 테스트를 통과하면 N장부터 시작해요!", 하단에 "시작하기"(브랜드 버튼)·"취소"(텍스트 버튼). 시작하면 문제 화면이 슬라이드로 들어오며 페이지가 서서히 걷히고, 취소·Android 뒤로가기는 페이지만 닫는다. 오답 3개 실패·피크 미사용 같은 규칙 문구는 두지 않음(심플하게). (미니강의는 §10)
  - **테스트 내용**: 챕터 N 카드를 눌렀다면 **직전 챕터(N-1)의 종합(키) 레벨 문제 세트**(예: 2장 카드 → 1-6, 3장 카드 → 2-8)를 그대로 푼다. 중간 챕터를 건너뛰어도 직전 챕터 종합만 출제.
  - **통과/실패**: 오답이 **3개째가 되면 바로 실패**(그 문제 채점을 보여 준 뒤 "다음" → 실패 화면). 오답 2개 이하로 끝까지 풀면 **통과**. **오답풀이는 하지 않는다.** 통과하면 **해금만** 한다(2026-10-28 변경): 챕터 N이 열리고(통과한 대상 챕터를 목록 `_skips`에 추가) 그 아래 모든 챕터의 **필수 레벨(종합 포함)이 한꺼번에 열리지만, 클리어 진행도(완료 횟수)는 하나도 채우지 않는다** — 퀘스트 보상을 직접 수행하지 않은 레벨에 주지 않기 위해, 클리어를 채우는 것은 유저 몫. 이미 쌓인 진행도는 그대로 유지. **이 테스트는 직전 챕터(N-1)의 종합 레벨 역할이므로 N-1의 선택 구간 첫 레벨(예: 2장 건너뛰기 → 1-7)은 함께 열린다**(그 뒤는 한 단계씩 클리어). 그보다 더 앞 챕터(N-2 이하)의 선택 구간은 종합 레벨을 직접 클리어해야 열린다. 통과한 챕터를 목록으로 저장하는 이유: 나중에 더 높은 챕터로 건너뛰어도 앞서 열린 선택 구간 첫 레벨이 다시 잠기지 않게. 실패는 진행 변화 없음.
  - **피크**: 소모도 환급도 **없다**. 결과 화면은 완주 화면을 재사용해 문구만 바꾼다(통과 "건너뛰기 통과!" + 트로피·색종이·보상음 / 실패 "아쉽게 통과하지 못했어요" + 오답 효과음, 트로피 없음). 문제 화면 타이틀 아래 배지는 "건너뛰기 테스트". 게이지는 오답풀이 몫이 늘지 않는다.
  - **남은 기회 표시**: 테스트 문제 화면의 **타이틀 오른쪽에 노란 하트 3개**(모양 = 앱이 쓰는 Phosphor `heart-fill`, 색 `#FFD60A` = 게이지 90%↑ 노랑 — `--icon-yellow`는 칙칙해서 제외, 크기 20px; 디자인은 사용자 승인 후 확정). 오답이 나올 때마다 오른쪽 하트부터 **회색(`--border`)**으로 바뀌어 남고(통통 튀는 효과 350ms), 3개 모두 회색이면 실패. 일반 레벨·오답풀이에서는 숨김. 타이틀 줄은 `.combo-v2-q-titlerow`(왼쪽 타이틀 / 오른쪽 하트).
  - 구현: `COMBO_V2_SKIP_MAX_WRONG`, `_comboV2StartSkipTest`, `comboV2SkipPass`, `_comboV2TestEnd`, 세션 `s.test = {to, level}`.
- **잠김 표시**: 잠긴 카드는 회색 + 자물쇠(JS가 추가·제거, `lucide.createIcons()` 재스캔), 도넛은 `aria-hidden`. 열리면 챕터 색 도넛 + `role="img"`.
- **저장**: 기기 로컬 `localStorage`(`chorditor_combo_progress_v1_<userId|anon>`, `{ "1-1": 2, ... }`). **서버 저장은 아직 없음**(기기 변경·앱 삭제 시 사라짐 — SQL 승인 후 별도).
- **개발 빌드(`_dev`) 전용 버튼**: 화면 왼쪽 아래에 "전체 열기"(토글, 모든 레벨 열림) / "진행 초기화". 정식 빌드에는 나오지 않고 문제 화면에서는 숨김.
- 검증(시뮬레이션): 신규 = 1-1만 열림 → 완료 2회까지 1-2 잠김 → 3회에 1-2 열림 → 1-6 클리어 시 1-7~1-14와 2-1 → 2장은 2-8이 키 레벨 → 3회 초과 기록은 3에서 멈춤 → 카드 DOM(열림·잠김·자물쇠·aria·도넛 호) 갱신·초기화 복구. 실제 화면 확인은 기기에서.

**챕터 해금**
- 정상: 이전 챕터의 키 레벨을 클리어하면 다음 챕터가 시험 없이 열림. 건너뛰기: 잠긴 챕터에 진입하면 챕터 시험(누적형: 그 챕터까지의 내용 전부 출제, 난이도는 직접 조정). 통과하면 현재 열린 곳부터 그 챕터까지가 전부 열리고, 건너뛴 챕터의 필수 레벨(키 레벨 포함)은 클리어 처리, 선택 레벨은 클리어로 치지 않되 키 레벨이 클리어라 열린 상태가 된다.

### 헤드 (`cd-head--sticky`)

- 왼쪽 도넛(44px): 안에 레벨 번호(챕터 색을 50% 어둡게 한 색), 링은 호 3개(두께 6px, 끝 둥글게, 맨 위에서 시계 방향). 채워진 호 수 = 완료 횟수, 모두 차면 클리어. **키 레벨(필수 구간 마지막 종합 레벨)은 호 5개**. 오른쪽에 레벨 제목.
- 카드 오른쪽 끝은 비워둔다(나중에 경험치 등 배치 예정).
- 제목이 두 줄이 되면 줄 길이를 균형 있게 나눈다(`word-break: keep-all` + `text-wrap: balance`). Chrome 114+, Safari 17.5+는 CSS로 처리하고, 그보다 낮은 웹뷰(구형 iOS·Android WebView)는 `chord-combo.js`의 `_comboV2BalanceTitles`가 줄 수를 유지하는 최소 폭을 찾아 `max-width`로 균형을 맞춘다(리사이즈·폰트 로드 시 재계산). 모바일 앱 기준이라 폴백이 필수.
- 탭하면 피크 소모 확인 모달(앱 표준 `showLeavePracticeModal`, "연습을 시작할까요?", 피크 -4(10문제 레벨) / -5(15문제 레벨), §4 피크 정산). Pro는 확인 생략. 스크롤 중 오작동 방지를 위해 `pointerup`이 아니라 `click`을 쓴다.
- 필수 구간(N-1~N-6): 흰 카드. 선택 구간(N-7~): 회색 카드 + 자물쇠 + 회색 글자(잠김). 현재 열림 상태는 §2. 열린 카드는 도넛 `role="img" aria-label="0/3"`·`--ch-accent` 스타일이 붙고 자물쇠 아이콘이 없다.
- 구간 사이에 안내 문구 "N-6을 클리어한 후 도전해요"를 가운데에 두고 좌우에 짧은 구분선을 붙인다. 같은 레벨 묶음이라 위아래 간격은 리스트 간격(12px)과 같다.

**이 화면에서 구현된 것**: 1~9장 챕터 카드 + 레벨 카드 세로 연결, 챕터 포인트 컬러 9색, 헤드의 9칸 챕터 점 줄(현재 원이 미끄러짐, 점 누르면 해당 챕터로 스크롤), 레벨 카드 도넛(완료 횟수 호 3개)·제목 균형 줄바꿈(CSS + 구형 웹뷰 JS 폴백), 탭 → 피크 확인 모달 → 문제 화면. 남은 것은 §9.

## 6. 문제 화면 디자인 — 연결형·배치형·교체형·분류형 (2026-10-26 확정, 목업은 `chord-combo.html`의 `#combo-view-quiz-v2`, CSS 접두어 `combo-v2`)

선택 화면에서 레벨 카드를 누르면 오른쪽에서 슬라이드 인 한다. 모든 레벨은 `COMBO_V2_LEVELS` 설정대로 실제 출제(§7)에 연결되어 있다(진입 가능 여부는 카드 열림 상태, §2). 문제 수는 한 판 본 문제 10개(챕터 4~는 15개, `_comboV2QCount`) + 오답풀이(§4).

- **제출 버튼**: 비활성 = 회색(`.cd-btn--gray`), 답을 다 채우면 **활성 = 브랜드색**(`--brand`, 차콜블랙, 흰 글자). 채점 후 정답이면 `#4CBB17`(선명한 연두), 오답이면 `#FF3B30`. 라벨은 "제출하기" → 채점 후 "다음", 마지막 문제는 "완료"(본 문제에서 오답이 있었으면 "다음" → 오답풀이 안내 화면, 없으면 클리어 화면. 오답풀이에서 틀리면 "다시 풀기", §4).

- **이탈**: X → 앱 표준 그만두기 모달 → 선택 화면 복귀, 짝·칩·채점 상태를 즉시 초기화(진행 중인 드래그·날아가기 효과도 정리).
- **안내 카드(`.combo-v2-info-card`, 연결형·배치형·빈칸형 공용)**: 타이틀 아래 흰 카드(`.cd-card`) 하나, 높이 120px 고정, 안쪽 패딩 16px, 글자 가운데 정렬. 문구는 **줄바꿈까지 패턴화**: 앞 문구 / (도수 줄) / 뒤 문구. 글자는 16px(`--type-title-sm`, 두께 400, 행간 140%, 회색), 도수·코드 줄만 20px(`--font-title-lg`, 두께 600, 진한 글자색, 항목 사이 16px 간격). 카드 아래 영역(빈칸 줄·짝 카드 묶음)은 **카드와 제출 버튼 사이의 정중앙**에 놓고 위아래 최소 24px을 확보한다. 문구 안의 `C key`는 그 문제의 key 이름(예: `Db key`)으로 바뀐다. 코드는 `_comboV2BuildInfoCard`.
- **안내 카드 강조(2026-10-27)**: 앞 문구의 `C key`(문제 key 이름)는 진하게(두께 800) 강조한다. 기능 문제(챕터 2)의 가운데 줄은 앞뒤 줄과 같은 16px 회색이고 **기능 이름(해결/예비/긴장)만** 진한 글자색 + 두께 800이다(따옴표 없음). 도수·코드 줄(20px)은 가운데 줄이 도수일 때만 쓴다. 구현: `_comboV2BuildInfoCard(card, head, degs, tail, midHtml)`.
- **도수 표기 규칙(2026-10-27, 모든 유형 공통)**: 로마숫자는 브랜드색(`--brand`)으로 강조하고, 뒤에 붙는 코드 퀄리티(`m` `M7` `/3` `add9` `m7(b5)` 등)는 항상 로마숫자보다 작고(약 50%, 최소 11px) 회색(`--text-secondary`)으로 톤다운한다. 퀄리티 안의 `( )`는 코드 이름과 마찬가지로 위첨자(`_ccFormatB5`). 자리별 크기: 연결형 카드 28/14, 안내 카드 도수 줄 20/11, 빈칸 아래 14/11, 칩·칸 안(반대 문제) 칩 글자/11. 채점 후 빈칸 아래 정답 도수는 칩 색(연두·빨강)을 그대로 쓴다. 모든 도수는 `_comboV2RomanHtml` 하나로 그린다.
- **문구 문법 규칙(전 챕터 공통, 2026-10-27)**: 안내 문구는 소리 내어 읽었을 때 문법에 어긋나지 않아야 한다. 강조한 말(코드 이름·도수·기능 이름) 뒤에는 반드시 조사를 붙이되, 받침에 따라 달라지는 조사(은/는, 이/가, 을/를)는 코드 이름(`A7`, `Dm` 등 읽는 소리가 제각각)에 직접 붙이지 말고 "코드"·"기능" 같은 받침이 고정된 일반 명사를 사이에 둔다(예: "**A7** 도미넌트 코드가", "**Dm** 코드를 향하는", "**예비** 기능의 코드를").
- **( ) 위첨자 규칙(코드 이름·도수 공통, 2026-10-27 재발 방지)**: `m7(b5)`, `add9(…)` 등 괄호 부분은 **반드시 `_ccFormatB5()`를 거쳐** `<sup class="cc-sup">`로 출력한다. 위첨자 크기는 컴포넌트별 CSS가 아니라 `style.css`의 전역 `.cc-sup` 한 규칙이 정한다(0.6em, 올림). 코드/도수 문자열을 `textContent`나 문자열 연결로 직접 화면에 넣지 말고 `_ccFormatB5`·`_comboV2Fmt`·`_comboV2RomanHtml`만 쓴다. 새 화면·컴포넌트를 만들면 코드가 표시되는 모든 위치(카드, 안내 문구, 칩, 고스트, 힌트)를 점검한다. (원인 2가지: ① 연결형 카드·안내 카드는 컴포넌트별 `sup` 규칙이 없어 브라우저 기본 sup(83%)로 나왔음 → 전역 `.cc-sup`. ② 카드·칩은 `display:flex`라 텍스트와 `<sup>`가 따로 flex 아이템이 되어 `vertical-align`이 무시됐음 → `_ccFormatB5`가 결과 전체를 `<span class="cc-chord">` 하나로 감쌈. **flex 컨테이너 안에 코드명을 넣을 때 sup을 형제 노드로 두지 말 것.**)
- **입체감**: 선택 전 = 솟음(위 안쪽 하이라이트 + 하단 단단한 모서리 + 바닥 그림자), 선택함 = 꺼짐(안쪽 위 그림자 + 2px 내려앉음, 가장자리 링 숨김).

### 연결형
- 문제 설명 "같은 짝끼리 이어주세요". **안내 카드 2줄**: "C key 다이어토닉 코드를" / "짝지어 주세요"(key 이름은 문제 key). 짝 카드 묶음은 안내 카드와 제출 버튼 사이 정중앙.
- 왼쪽 열 = 코드 이름, 오른쪽 열 = 로마자 도수. 카드는 흰 `.cd-card` 버튼(최소 높이 72px), 글자 28px / 두께 600, 로마숫자 28px + 코드 퀄리티 16px(같은 기준선). 열 사이 32px(다른 묶음), 같은 열 카드 사이 12px. 두 열은 세로 가운데 배치, 서로 독립적으로 섞인다.
- 조작: 카드를 탭해 선택 → 반대편 열 카드를 탭하면 짝이 된다. 선택 중·짝지어진 카드는 꺼진 상태. **짝마다 다른 색**(`--icon-blue` → `--icon-purple` → `--icon-yellow` → `--icon-pink` 순. 정답(연두)·오답(빨강)과 헷갈리지 않도록 빨강·초록 계열 제외. 핑크는 오답 빨강과 가까워 4번째 짝에서 구분이 약하면 주황·청록으로 교체 검토) — 테두리 2px(색 45% + 흰색)와 은은한 배경(색 12% + 흰색). 같은 열 카드를 다시 탭하면 선택만 바뀌고, 이미 짝인 카드를 탭하면 그 짝이 풀린다. 전부 짝지으면 제출 활성. 어느 쪽을 먼저 눌러도 되므로 "코드→도수 / 도수→코드" 방향 구분은 두지 않는다.

### 배치형
- 문제 설명 **"주어진 진행에 맞게 배치하세요"**(반대 문제는 "주어진 진행에 맞게 도수를 배치하세요"). 부가설명 줄은 없고 **안내 카드 3줄**: "C key 다이어토닉 코드에서" / "I IV V VIm"(빈칸 아래 도수와 같은 값, 20px) / "순서대로 코드를 나열해주세요". 코드 진행은 코드 반주 훈련 데이터에서 뽑는다(§7-1).
- **빈칸**: 밑줄 + 아래 로마자뿐(칩 모양 아님), 밑줄은 칩 아래 4px. 로마자는 로마숫자 + 퀄리티(같은 기준선, 한 덩어리로 감싸서 정렬), 텐션 `(...)`은 위첨자. **스피커 아이콘은 안내 카드 좌상단**(카드 모서리에서 아이콘까지 16px, 터치 44px, 색 = 챕터 색 `--ch-accent`) — 누르면 정답 진행을 재생(§8). 교체형·빈칸형 카드에도 같은 스피커.
- **코드 풀**: 바닥에 붙고(제출 버튼 위 24px) 가로 스크롤 없이 한 줄 4개, 최대 2줄. 줄 간격 16px, 풀 한 줄의 폭은 빈칸 줄 안쪽 폭과 같다. 풀 칩은 쓰고 나서도 사라지지 않는다(복사본이 빈칸으로 이동).
- **칩**: 풀과 빈칸 안 칩의 폭·높이·글자가 같고 모서리 8px. 코드 이름의 `(...)`는 위첨자(기존 `_ccFormatB5`). 터치 영역은 위아래만 확장해 44px.
- **채우기**: 풀 칩을 탭하면 복사본이 0.4초 동안(`cubic-bezier(0.22, 1, 0.36, 1)`) 날아가 **비어있는 칸의 가장 왼쪽**에 놓이고 통통 튄다. 4칸이 다 찼을 때 탭하면 흔들린다.
- **제거**: 채운 칩을 짧게 탭하면 0.18초 동안 작아지며 사라진다. 중간 칸을 비우면 그 칸은 밑줄 + 로마자만 남고 나머지는 제자리(구멍 유지).
- **이동**: 0.2초 이상 누른 채 움직이면 드래그(고스트가 따라옴). 홀드 전에 8px 넘게 움직이면 탭도 드래그도 아닌 것으로 취소. 기존 드래그 방식(고스트 클론 + `elementFromPoint`)을 따랐다.
- **드래그 중 미리 교체(2026-10-27, 분류형과 같은 방식)**: 든 칩이 다른 칸 위에 **90ms 이상 머물면** 그 칸의 칩이 바로 든 칩의 원래 칸으로 옮겨 가고(0.32초 이동, 빈칸이면 빈 자리가 옮겨 감) 든 칩은 그 칸에 들어간 것으로 친다. 칸 밖으로 나가거나 원래 칸으로 돌아오면 드래그 시작 때 상태로 복귀. 놓으면 그 상태가 확정되고 놓은 칩이 고스트 위치에서 제자리로 들어온다. 칸 판정은 좌우 10px·위아래 28px 넓혀 칸 사이 틈에서 깜빡이지 않게 하고, 칸이 겹치면 중심이 가까운 칸. 상수 `COMBO_V2_HOVER_MS` / `COMBO_V2_HOVER_PAD_X` / `COMBO_V2_HOVER_PAD_Y`. 시스템 제스처·이탈 시 시작 상태로 복구.
- **칩 크기 (뷰포트 5단계, 정수 px)**: 360~480px = 칩 폭 (본문 폭 − 그리드 마진×2 − 간격×3) ÷ 4(360px에서 76, 상한 92) × 높이 32, 글자 13(채점 항목 참조), 칸 간격 8, 좌우 여백 0(스피커가 카드로 올라가 여백 불필요), 로마자 14/11, 풀 한 줄·빈칸 줄 328 / 481px~ 92×40·글자 16·간격 8·로마자 16/12 / 769px~ 100×40·간격 20 / 1080px~ 108×44·글자 17·로마자 17/13. 빈칸형 선택지 카드 폭 = (4×칩폭 + 간격) ÷ 3(360px에서 104). 1·2단계는 본문 폭을 칩으로 꽉 채우고 3단계부터는 칩 폭을 글자 길이에 맞춰 남는 폭을 줄 양옆 여백으로 둔다(가운데 정렬). 글자 증가폭은 스타일가이드의 "모바일 대비 4px 이내", 칸 간격은 그 구간 그리드 마진을 넘지 않게. 가장 긴 예상 이름 `C#7sus4(9)`는 글자 1em당 약 4.45em라 13px에서 약 58px로 칩 76px에 들어간다.
- **채점**: 칩마다 정오답(위 공통). 이번 목업은 틀린 칩에 정답을 알려주지 않는다. 칩 글자는 모바일(360px)에서도 **16px**(481px~는 원래 16~17px)로 올렸다(2026-10-27; 날아가는·드래그 복제본은 원본 글자 크기를 복사). 긴 이름(`C#7sus4(9)`)이 나오는 챕터에서는 칩 폭을 같이 키워야 한다.

### 교체형 (빈칸 채우기 / 특정 칸 교체하기, 딱 1칸만 맞춤)
- 두 가지 모드: **교체형**(표시된 칸을 다른 코드로 바꿈)과 **빈칸형**(빈칸에 알맞은 코드를 넣음). **챕터 1은 빈칸형(`mode: 'fill'`)만 쓰고** 교체형은 챕터 2 이후에서 쓴다. 타이틀은 교체형 "표시된 부분을 바꿔주세요", 빈칸형 **"빈칸에 알맞은 코드를 배치하세요"**(반대 문제는 "…도수를 배치하세요").
- **안내 카드**: 타이틀 아래 안내 카드(공용). 빈칸형 2줄 "C key 다이어토닉 코드에서" / "빈칸에 알맞은 코드를 채워주세요", 교체형 3줄 "C key 다이어토닉 코드에서" / "IV → IIm"(20px) / "코드로 교체해주세요". 스피커는 카드 좌상단. (챕터별 문구는 §7)
- **코드 줄**: 배치형과 같은 4칸 폭·간격. 안 바뀌는 칸은 칩 없이 **순수 텍스트**(칩과 같은 글자 크기)이고, 바꿀(채울) 칸만 칩. **모든 칸에 밑줄을 둔다**(채워진 칸도, 2026-10-27). 칸 아래에는 로마자를 표시하되 **교체형은 바꿀 칸 아래를 비우고, 빈칸형은 빈칸 아래에도 로마자를 표시**한다. 글자는 모바일에서도 16px.
- **선택지**: 정답 1 + 오답 2 = 3개, 한 줄. 오답은 해당 키 다이어토닉 7화음에서 정답을 뺀 후보 중 랜덤 2개(교체형은 **원래 코드도 후보에서 제외**), 정답 위치도 섞는다. 문제가 시작될 때마다 새로 뽑는다(챕터 1은 그 문제 key의 7화음에서). 카드 폭 = 빈칸 줄 안쪽 폭을 3등분(정수 px: 360 → 88, 481 → 125, 769 → 140, 1080~ → 150), 높이 = 칩 높이 + 12px(44 / 52 / 52 / 56 / 56), 칩 글자·간격은 배치형 값 그대로.
- **조작**: 선택지를 탭하면 바꿀 칸 칩의 코드가 바로 바뀐다(날아가기 없음, 기존 통통 효과). 선택된 카드는 연결형처럼 꺼진 상태, 다른 카드를 탭하면 선택이 옮겨진다. 선택 전에는 제출 비활성(빈칸형은 칩 없이 밑줄만 보이다가 선택하면 칩이 생김).
- **채점**: 바꿀 칸 칩만 정답 연두 / 오답 코랄로 바뀌고, 그 아래에 **정답 도수(예: IIm)가 칩 테두리와 같은 색(`#4CBB17` / `#FF3B30`)으로 표시**된다(오답이어도 표시되는 것은 정답의 도수). 채점 후 선택지 잠금, 제출 버튼은 "다음"/"완료".

### 분류형 (2장 전용 — 코드 7개를 해결/예비/긴장으로 나눔)
- 문제 설명 "코드의 기능별로 분류해주세요", 부가설명 없음. 목업 데이터는 C key: 해결(토닉, I) = C·Em·Am, 예비(서브도미넌트, IV) = F·Dm, 긴장(도미넌트, V) = G·Bdim.
- **헤더(3열)**: 1줄 해결 / 예비 / 긴장(`--type-title`, 두께 700), 2줄 캡션 토닉 / 서브도미넌트 / 도미넌트(`--font-body-sm`, 회색), 3줄 로마자 I / IV / V(`--type-title-sm`). **영어판은 이름과 겹치므로 캡션을 숨긴다**(`html[lang="en"]` 규칙 — 앱에 언어 속성 설정이 아직 없어 연결 필요). 헤더는 카드 없이 텍스트만(카드로 묶어 보았으나 채택하지 않음).
- **열 레인**: 열 폭으로 본문 폭을 3등분해 꽉 채운다(열폭×3 + 열간격×2 ≤ 본문 폭: 360 → 104/8, 481 → 144/8, 769 → 235/12, 1080~ → 256/16). 레인은 연한 회색 영역(검정 4%, 모서리 12px, 안쪽 패딩 8px)이고, 칩이 위에서부터 **겹치지 않고 아래로 쌓인다**(칩 간격 8px). 칸 수 제한과 빈 슬롯 표시는 없다(3/2/2 개수가 노출되지 않도록). 최소 높이는 칩 3개, 더 쌓이면 늘어난다. **문제 영역(3열 그리드 전체)은 높이 400px 상한**을 두고, 남는 높이는 위아래로 나눠 가운데에 놓는다(풀과 최소 간격 16px).
- **칩**: 높이 48 / 52 / 56 / 56, 글자 18 / 20 / 22 / 22px(360 / 481 / 769 / 1080~, 레인·풀 공통). 레인 칩은 레인 폭을 채우고, 터치 영역 확장은 이웃과 겹치지 않도록 끈다(높이 자체가 44px 이상).
- **안내 말풍선**: 풀 좌상단(본문 왼쪽 끝, 풀 위)에 "꾹 눌러서 드래그하세요!". 배경은 챕터 색 15% + 흰색 85% 단색, 글자는 진한 챕터 색(챕터 색 50% + 검정 50%), 13px 두께 600, 모서리 12px, 꼬리는 아래(풀 쪽) 6px. 풀의 칩이 모두 분류돼 비면 숨긴다.
- **코드 풀(바닥 한 줄)**: 본문 폭 전체, 칩은 가운데 정렬, 칩 폭은 글자 길이(최소 56px, 좌우 패딩 16px), 간격 8px. 대기열은 순서가 있는 목록이고 **앞에서부터 한 줄에 들어가는 만큼만 만든다(넘치면 생성하지 않음)**. 분류할 때마다 빈 폭만큼 다음 칩이 나타나고, 처음 순서는 섞는다. 풀 칩만 탭하는 것은 동작 없음(드래그 전용).
- **분류(풀 → 레인)**: 0.2초 홀드 후 드래그. 원본은 풀에서 반투명으로 남고 고스트가 따라온다. 레인 위에 있으면 그 자리에 **빈자리(검정 7% 상자)가 열리며 아래 칩들이 FLIP 방식으로 밀려난다**(0.22초, 일반적인 sortable 정렬 방식). 놓으면 고스트가 그 자리로 들어가고 풀에서 칩이 빠지며 나머지가 왼쪽으로 슬라이드. 레인 밖에 놓으면 원위치.
- **되돌리기**: 레인 칩을 짧게 탭하면 풀 **맨 앞(왼쪽)**으로 돌아가고, 한 줄에 못 들어가게 밀린 오른쪽 칩은 페이드아웃으로 잠시 사라진다(다음 분류 때 다시 나옴). 레인 안·레인 사이 이동도 같은 홀드 드래그 + 빈자리 방식.
- **채점**: 풀과 대기열이 다 비어야 제출 활성. 칩이 맞는 열에 있으면 민트, 아니면 코랄(열 안 순서는 무관), 이후 잠금.

- **key 라벨(2026-10-27)**: 분류형 상단(타이틀 아래, 3열 헤더 위)에 `C key`를 가운데 정렬 24px / 두께 700으로 표시한다(어느 key의 코드인지 알려 줌, 종합 레벨에서 필요).
- **채점·진행(챕터 2~)**: 전부 맞으면 정답, 하나라도 틀리면 오답으로 세고(진행 막대는 맞든 틀리든 한 칸 참) 오답풀이 몫이 전체에 더해진다. 제출 후 버튼은 "다음"/"완료"(본 문제는 재시도 없음, 오답풀이에서만 "다시 풀기" — §4).

## 7. 출제 로직 (챕터별, `chord-combo.js`, 2026-10-27 구현)

레벨 번호를 누르면 `COMBO_V2_LEVELS[레벨]` 설정으로 한 판(본 문제 10개, 챕터 4~는 15개)을 만든다. 공통 엔진은 7-1, 챕터별 규칙은 7-2~7-8. 챕터별 문구·반대 문제·진행 규칙의 세부는 각 절에 있다.

### 7-1. 공통 엔진과 챕터 1

레벨 번호를 누르면 `COMBO_V2_LEVELS[레벨]`의 설정({keys, kinds})으로 한 판(본 문제 10개, 챕터 4~는 15개)을 만든다. 코드 진입점은 `comboV2EnterQuiz` → `comboV2SetType(설정)` → 문제마다 `_comboV2QShow(유형)`, 제출 후 "다음" → `_comboV2Next()`, 본 문제를 다 풀면 오답이 있으면 `_comboV2ShowIntro()`(안내) → `_comboV2StartReview()`, 없으면 `_comboV2Finish()`(클리어 화면 → "확인" → `comboV2ExitQuiz()`).

**레벨 구성 (`COMBO_V2_LEVELS`)**
- **1-1~1-6 = 연결형 + 빈칸형**(`COMBO_V2_KEY_KINDS`): 1-1 C, 1-2 G, 1-3 D, 1-4 A, 1-5 E, **1-6 = C·D·E·G·A 랜덤(5key 종합)**.
- **1-7 이후(도전 레벨) = 연결형 + 배치형 + 빈칸형**(`COMBO_V2_MIX_KINDS`): 1-7 F, 1-8 Bb, 1-9 B, 1-10 Db, 1-11 Eb, 1-12 Gb, 1-13 Ab, 1-14 12key 챌린지. 옛 코드진행 레벨은 없다(2026-10-27 삭제).
- 분류형·교체형은 챕터 1에 나오지 않는다(챕터 2~).
- 레벨 설정을 바꾸려면 이 표만 고친다. 레벨 카드에는 `data-level="N-M"`이 있어야 눌렀을 때 진입한다.

**한 판 구성**
- **유형 균등 분배**: 유형 목록을 본 문제 수에 균등하게 나눈다(나누어떨어지지 않으면 어느 유형이 하나 더 많을지는 랜덤). 순서는 섞는다.
- **key**: key가 여러 개인 레벨은 문제마다 랜덤으로 섞되 **바로 앞 문제와 같은 key는 피한다**.
- **진행 중복**: 배치형·빈칸형은 같은 진행이 다시 나올 수 있으나 **바로 앞 문제와 같은 진행은 피한다**(유형이 달라도 공유, `prevId`).
- 정답 수는 `_comboV2Sess.correct`에 세지만 보여 주는 결과 화면은 아직 없다(§9).

**key 일반화**
- 12key를 `COMBO_V2_KEYS`에 정의(이름·C 기준 반음·플랫 표기 여부: Db Eb F Gb Ab Bb는 플랫, 나머지는 샵/자연).
- 코드 이름은 기존 `degreeToChordName`(chord-combo-questions.js)이 도수 → 코드로 변환한다. 12key 결과 예: Db = Db Ebm Fm **Gb** Ab Bbm Cdim / Gb = Gb Abm Bbm **B** Db Ebm Fdim / B = B C#m D#m E F# G#m A#dim. **Gb key의 IV는 정석 표기 `Cb`가 아니라 `B`로 나온다**(앱의 기존 표기 규칙을 따른 것, **확정**: `Cb`는 `B`, `Fb`는 `E`로 표기).
- 도수는 `COMBO_V2_DEGS`: I IIm IIIm IV V VIm VIIdim.

**도수 출제 빈도**
- 도수별 가중치 `w`: I 5 · IIm 4 · IIIm 3 · IV 5 · V 5 · VIm 4 · VIIdim 1. 뽑힐 확률은 w에 비례(`_comboV2WeightedPick`, 한 문제 안에서는 비복원).
- 연결형은 한 문제에 4개를 뽑으므로 한 문제에 나올 확률은 가중치보다 평평하다(시뮬레이션: I 70% / IIm 61% / IIIm 50% / IV 70% / V 70% / VIm 61% / VIIdim 19%).

**연결형 (`_comboV2PairPick` / `_comboV2PairBuild`)**
- 짝 개수: **3개 70% / 4개 30%**(`COMBO_V2_PAIR3_RATE`).
- **VIIdim(dim)은 항상 짝 3개짜리에만 나온다**(`only3`): 4개로 뽑았는데 VIIdim이 들어 있으면 나머지 중 하나를 무작위로 빼서 3개로 만든다. 그 결과 3개짜리 비율은 약 76%.
- 한 판 안에서 같은 도수 조합(같은 key)은 다시 나오지 않는다(최대 50회 재추출). 왼쪽(코드)·오른쪽(도수) 열은 독립적으로 섞는다.
- 안내 카드: "{key} key 다이어토닉 코드를 / 짝지어 주세요".

**진행 데이터 (배치형·빈칸형 공통)**
- 코드 반주 훈련의 진행 데이터 `progression-data.js`(`PROGRESSION_DATA`)를 `chord-combo.html`에서 로드한다(`progression-parser.js`는 불필요).
- 필터(`_comboV2SwPool`): 챕터 1은 `no` 1(기초), Major, C key로 적힌 진행 중 **다이어토닉 3화음 7개로만 된 것**(21개, 전부 4코드). **챕터 2 이후는 `no` 제한 없이 3화음·7th 진행 30개**를 쓴다(7th 레벨은 전부 7th로 치환). 진행은 도수 기반이므로 `roots`(연주 가능한 key)는 보지 않고, C key 코드를 도수로 바꿔(`COMBO_V2_C_CHORD_DEG`) 그 문제의 key 코드로 옮겨 쓴다. 반주 훈련에 진행을 추가하면 문제에도 자동 반영된다.
- 같은 코드가 반복된 진행(IV V I I)도 4칸 전부 표시한다.

**빈칸형 (`_comboV2SwGen` / `_comboV2SwBuild`)**
- 진행 4코드를 전부 보여 주고 **빈칸은 항상 1개**. 정답 도수는 위 가중치로 고르고(진행에 든 도수끼리 경쟁), 그 도수가 놓인 자리 중 하나가 빈칸.
- 선택지는 정답 1 + 오답 2(그 key의 다이어토닉 7화음에서 정답을 뺀 후보 랜덤 2개), 위치는 섞음. 칸 아래에는 빈칸 포함 전부 로마자 표기.

**배치형 (`_comboV2PlaceBuild`)**
- 진행 4코드가 4칸(정답), 칸 아래에 로마자 힌트. 코드 풀은 그 key의 다이어토닉 7화음(도수 순서). 같은 코드가 두 칸에 있으면 풀 칩을 두 번 써서 채운다(풀 칩은 사라지지 않음).

**반대 문제 (배치형·빈칸형만, `COMBO_V2_REVERSE_RATE` = 20%)**
- 보통은 도수를 보고 코드를 맞추고, **반대는 코드를 보고 도수(로마숫자)를 맞춘다**. 빈칸형 반대: 칸에 도수, 아래 힌트가 코드 이름, 선택지가 도수 3개. 배치형 반대: 칸 아래에 코드 이름 힌트, 풀이 도수 칩 7개(I~VIIdim), 안내 카드 가운데 줄이 코드 진행. 타이틀·안내 문구도 "도수"로 바뀐다.
- 연결형은 원래 양방향이라 대상이 아니다. 20%로 줄인 이유: 30%는 체감 빈도가 높았음.

**세션 상태 (`_comboV2Sess`)**: `idx`(현재 문제) · `correct` · `kinds`(문제별 유형) · `cfg`(레벨 설정) · `key`/`dia`(현재 key와 7화음) · `prevKey` · `prevId` · `used`(연결형 조합) · `reverse`.

**챕터 3 — 코드 꾸미기** `{keys, ch3: 'both'}`
- 문제마다 테마를 정한다: **꾸밈코드** 또는 **전위코드**(종합 'both'는 3:2 또는 2:3 랜덤, `'deco'`/`'inv'` 단독 설정도 가능). 테마별로 유형을 한 바퀴씩 돌려 균등 분배.
- **꾸밈코드 테마**: 연결형·배치형·빈칸형(**교체형은 너무 쉬워 제외**, 분류형 없음), **7th 없음**. 꾸밈코드 = I에 add9·sus2·sus4, IV에 add9·sus2, V에 add9·sus2·sus4. IV sus4는 4도 음 Bb이 다이어토닉 밖이라 제외. **모든 문제에 꾸밈코드 1개 이상**: 연결형은 꾸밈코드를 먼저 뽑고 나머지를 채움, 배치형은 진행의 1~2칸을 꾸밈코드로 바꿈. **I sus4는 바로 뒤 칸이 꾸미지 않은 I일 때만 출제**(`Csus4 → C`), V sus4는 제약 없음. 배치형 코드 풀은 정답 코드 + 오답으로 채워 최대 8개(2줄).

C key 기준 `I/3`(베이스 E) 뒤에는 IV·IIm·IIIm만, `IV/3`(베이스 A) 뒤에는 V·VIm·VIIdim만, `V/3`(베이스 B) 뒤에는 I·VIm·VIIdim만 온다(`C/E → G`, `F/A → C`는 탈락, `C/E → F`, `F/A → G/B`는 통과). 이 규칙을 만족하는 칸이 없는 진행은 다시 뽑고, 교체형은 정답 전위가 다음 코드와 이어지는 칸만 대상으로 한다. **전위가 진행에 들어가는 모든 곳에 공통 적용**: 챕터 3 전위 테마, 챕터 7의 4코드 1전위 진행(`_comboV2InvOk`). 챕터 6의 1전위는 연결형(짝 맞추기)에만 나오고 진행에는 안 들어간다.

### 7-3. 챕터 4 (세컨더리 도미넌트)

레벨 설정 `COMBO_V2_LEVELS['4-N']` = `{keys, kinds: 연결형·배치형·교체형·빈칸형, ch4: true}`. 레벨은 챕터 1·5·7·9와 같은 구조(한 레벨 한 key, 4-6 종합 = 키 레벨, 4-7~4-13 선택 key, 4-14 12key 챌린지). 한 판 본 문제 10개(챕터 4~는 15개), 4유형 균등 분배(나머지 1문제는 랜덤 유형). 3화음/7th 배분은 적용하지 않음(도미넌트만 7th, 나머지는 3화음).

**핵심 코드 = 도미넌트 6종 (`COMBO_V2_DOMS`)**: 프라이머리 `V7`(타겟 I) + 세컨더리 `V7/II`(타겟 IIm) `V7/III` `V7/IV` `V7/V` `V7/VI`. C key: G7 A7 B7 C7 D7 E7 (타겟 C Dm Em F G Am). 코드 이름은 기존 `degreeToChordName`(VI7=A7 …), 12key 전부 지원. 도수 표기는 `V`·타겟 로마숫자는 크게(브랜드색), `7`과 `/`는 작은 회색(`_comboV2RomanHtml`).

**진행 규칙 (배치형·교체형·빈칸형)** — 진행은 코드 반주 훈련 데이터의 다이어토닉 진행을 3화음으로 치환해 쓰고(`no` 제한 없음), 그중 한 칸을 도미넌트로 바꾼다(`_comboV2Ch4Prog`).
1. 진행에 도미넌트7 코드는 **정확히 1개**.
2. 프라이머리 도미넌트도 포함(바로 뒤 칸이 I이면 `V7`).
3. **첫 칸은 도미넌트가 될 수 없음**.
4. 도미넌트의 타겟 = 바로 뒤 칸. **마지막 칸이면 첫 칸으로 순환**. 타겟이 VIIdim인 칸은 제외.
   - **배치형에서는 타겟 코드를 항상 미리 표시**(글자 고정)해서 길을 찾기 쉽게 한다(2026-10-27; 챕터 4·5·6 공통). 챕터 4 배치형은 도미넌트의 타겟 칸이, 챕터 6 배치형은 각 투-파이브의 타겟 칸(마지막 마디면 첫 칸)이 고정된다.
5. 반대 문제(코드 ↔ 도수) 출제 가능(배치형·빈칸형 20%). 연결형·교체형처럼 의미 없는 곳엔 적용하지 않음.
6. 문구는 조사까지 문법에 맞춤(§6 공통 틀의 문구 문법 규칙).

**유형별**
- **연결형**: 도미넌트 6종 중 3개(70%) / 4개(30%). 변형 2가지를 랜덤: (a) **도미넌트 코드 ↔ 타겟 코드**(A7 ↔ Dm) "C key에서 도미넌트 코드와 / 그 타겟 코드를 짝지어 주세요" (b) **도미넌트 코드 ↔ 도수**(A7 ↔ V7/II). **두 변형 모두 도미넌트 코드가 항상 왼쪽 열**(도미넌트 → 타겟 순서로 읽히게; 오른쪽에서 읽는 언어권이면 반대로 뒤집어야 함) "C key에서 도미넌트 코드와 / 알맞은 도수를 짝지어 주세요".
- **배치형**: 진행 4칸(도미넌트 1개 포함)을 코드 풀에서 채움. 풀은 정답 코드 + 다이어토닉 7화음·도미넌트 6종에서 채워 최대 8개. 칸 아래 도수 힌트에 `V7/II`가 나옴. 반대(20%): 도수 칩 배치.
- **교체형**: 한 칸을 바로 뒤 타겟을 향하는 도미넌트로 교체. 정답 1(그 타겟의 도미넌트) + 오답 2(다른 도미넌트). "C key 코드진행에서 / **Dm** 코드를 향하는 도미넌트로 / 교체해주세요". 반대 없음. 채점 후 정답 도수(`V7/II`)가 칩 아래에 표시됨.
- **빈칸형**: 도미넌트 칸을 비우고 아래 도수 힌트(`V7/II`)로 코드를 고름. 정답 1 + 오답 2(다른 도미넌트). "C key 코드진행에서 / **Dm** 코드로 향하는 / 도미넌트 코드를 채워주세요"(교체형과 마찬가지로 타겟 코드를 알려 줌).
  - **반대 빈칸형(20%) = 도미넌트 역할 맞추기**: 진행(다이어토닉은 코드 이름 + 아래 도수)에서 도미넌트 코드를 보여 주고(빈칸 아래 힌트 = 그 코드), 도수 선택지(`V7` 프라이머리, `V7/II` … 세컨더리 몇 도 타겟인지)에서 고름. "C key 코드진행에서 / **A7** 도미넌트 코드가 / 무엇의 도미넌트인지 골라주세요".

### 7-4. 챕터 5 (릴레이티드 투-마이너)

레벨 설정 `COMBO_V2_LEVELS['5-N']` = `{keys, kinds: 연결형·배치형·교체형·빈칸형, ch5: true}`, 구조는 챕터 4와 같음(5-6 종합 = 키 레벨, 5-14 12key 챌린지). 한 판 본 문제 10개(챕터 4~는 15개), 4유형 균등 분배.

**투마이너** = 도미넌트의 완전5도 위(= 타겟의 2도). 타겟이 메이저(I·IV·V)면 `m7`, 마이너(IIm·IIIm·VIm)면 `m7(b5)`. 프라이머리(타겟 I)는 다이어토닉 `IIm7`. C key: Dm7→G7→C / Em7(b5)→A7→Dm / F#m7(b5)→B7→Em / Gm7→C7→F / Am7→D7→G / Bm7(b5)→E7→Am. **도수 표기는 정석에 없어 자체 표기 `Rel.IIm →`**(`Rel.`은 로마숫자와 같은 크기의 회색, `m`은 작은 회색, `II`는 브랜드색, 화살표는 진하게; 뒤의 도미넌트로 이어진다는 느낌). 어느 타겟의 투마이너인지는 같은 줄의 도미넌트 라벨(`V7/VI` 등)이 알려 줌. 6종 모두 같은 라벨이라 연결형 짝 식별은 타겟 도수로 한다.

**투마이너 출제 빈도(2026-10-27)**: 타겟 도수별 가중치 `COMBO_V2_RII_W` — C key 기준 Dm7 2 · Em7(b5) 3 · F#m7(b5) 1 · Gm7 5 · Am7 2 · Bm7(b5) 7(= 타겟 I 2 · IIm 3 · IIIm 1 · IV 5 · V 2 · VIm 7, 12key 모두 같은 비율). 연결형은 이 가중치대로 3~4개 비복원 추출, 진행 문제는 투-파이브를 넣을 위치(= 타겟 투마이너)를 이 가중치로 고르며 투-파이브가 2개인 8코드 진행에서 묻는 쪽도 가중치로 고름. 마지막 칸 투-파이브의 타겟은 항상 첫 코드(순환).

**4코드 / 8코드 배분 (2026-10-27)**: 진행이 나오는 문제(배치형·교체형·빈칸형; 연결형은 진행이 없어 제외)를 순서대로 놓고 **앞쪽 60%는 4코드 진행, 뒤쪽 40%는 8코드 진행**(`COMBO_V2_CH5_BIG_RATE`, 4코드 문제 수 = 반올림(대상 문제 수 × 0.6)이라 문제 수가 늘어도 자동 적용; 예: 진행 문제가 10개면 6:4).
- **4코드 진행**: 투-파이브 1개가 두 칸(투마이너 + 도미넌트)을 차지하고 타겟은 그 바로 다음 칸. 위치는 (1·2칸 → 타겟 3칸) / (2·3칸 → 타겟 4칸) / (3·4칸 → 타겟이 첫 코드로 순환). 도미넌트는 첫 칸에 오지 않음. 예: `Dm7 G7 Am F`처럼 한 줄 4칸.

**8코드 진행 (`_comboV2Ch5Prog`)**
- 4코드 진행(다이어토닉 3화음, `no` 제한 없음)을 두 배로 늘려 반 마디씩 8칸으로 만들고, **같은 코드가 이어지면 `%`** 로 표기(예: `C % Bm7(b5) E7 Am % Gm7 C7`). 4칸씩 두 줄로 표시.
- 일부 마디를 투-파이브(투마이너 + 도미넌트)로 바꾼다. **한 진행에 1~2개**(2개는 30%, 이때 마디 2·4), 첫 마디는 제외(챕터 4 규칙 3 유지). 타겟 = 바로 다음 마디의 코드이고 VIIdim은 타겟 불가. 투-파이브끼리 이웃하지 않음.
- **마지막 마디의 투-파이브는 타겟이 항상 첫 코드로 순환**한다(이전에 허용했던 "진행에 없는 코드" 예외는 2026-10-27 폐지 — 마지막 칸에 문제를 내면 반드시 첫 칸과 순환). 첫 코드가 VIIdim이면 마지막 마디에는 투-파이브를 넣지 않음.
- **물어보는 투-파이브는 1개**로 제한(2개짜리 진행이어도 나머지는 글자로 고정). 도미넌트는 묻지 않고 **투마이너를 묻는다**.

**유형별**
- **연결형**: 투마이너 6종 중 3개(70%) / 4개(30%). 변형 2가지 랜덤: (a) 투마이너 ↔ 도미넌트(Bm7(b5) ↔ E7) "C key에서 투마이너 코드와 / 그 도미넌트 코드를 짝지어 주세요" (b) 투마이너 ↔ 타겟 코드(Bm7(b5) ↔ Am) "… / 그 타겟 코드를 짝지어 주세요". 투마이너(시간상 먼저 오는 코드)가 항상 왼쪽 열.
- **배치형**: 8칸 중 `%`·다이어토닉 코드·도미넌트·묻지 않는 투-파이브는 모두 글자로 고정(`combo-v2-fixcell`), **빈칸은 물어보는 투마이너 1개뿐**(4코드·8코드 공통). 코드 풀 = 정답 코드 + 다이어토닉·투마이너 오답, 최대 8개. 반대 문제 없음. "C key 코드진행에서 / 빈칸에 알맞은 코드를 배치해주세요".
- **교체형**: 도미넌트 바로 앞 칸(원래 코드가 칩으로 보임)을 그 도미넌트의 투마이너로 교체. 정답 1 + 오답 2(다른 타겟의 투마이너). "C key 코드진행에서 / **E7** 도미넌트 코드 앞의 칸을 / 투마이너 코드로 교체해주세요". 반대 없음.
- **빈칸형**: 투마이너 칸을 비우고(힌트 `Rel.IIm →`) 코드를 고름. "… / **E7** 도미넌트 코드 앞에 오는 / 투마이너 코드를 채워주세요". **도수 찾기(반대) 문제는 챕터 5 전체에서 제외**(2026-10-27).
- 분류형 없음. 3화음/7th 배분 적용 없음(투마이너·도미넌트만 7th).

**구현 메모**: 빈칸 수가 문제마다 달라서(챕터 2~4는 4칸 고정) 배치형 슬롯 수를 고정 4에서 실제 빈칸 수로 바꿈. `%` 칸은 글자 고정, 칸 아래 도수 없음.

### 7-5. 챕터 6 (도미넌트의 대리코드)

레벨 설정 `COMBO_V2_LEVELS['6-N']` = `{keys, kinds: 연결형·배치형·교체형·교체형, ch6: true}`. 한 판 본 문제 10개(챕터 4~는 15개). **빈칸형은 출제하지 않고 교체형을 두 배로 둔다**(주제가 "이 코드가 이렇게 바뀐다"라서; 빈칸형 코드는 보존) — 한 판에 교체형 2~3개, 연결형·배치형 1~2개. 핵심 = **이미 도미넌트가 있는 진행에서 그 도미넌트를 대리코드로 바꾸는 것**.

**대상: 도미넌트 6종(프라이머리 포함)** — C key: G7 A7 B7 C7 D7 E7 (챕터 4 `COMBO_V2_DOMS`와 같음). 코드마다:
- **3도 위 dim7**(장3도 위 루트, 항상 `#` 표기): Bdim7 C#dim7 D#dim7 Edim7 F#dim7 G#dim7. 도수는 **그 key의 1도 기준 절대 도수**: `VIIdim7` `#Idim7` `#IIdim7` `IIIdim7` `#IVdim7` `#Vdim7`(세컨더리와 무관).
- **1전위**: G7/B A7/C# B7/D# C7/E D7/F# E7/G#.
- **트라이톤 대리 도미넌트**(타겟 +1반음, 항상 `b` 표기, **챕터 6은 텐션 없이**): Db7 Eb7 F7 Gb7 Ab7 Bb7. `(#11)`은 챕터 7에서 텐션으로 붙인다(2026-10-27 변경). 표기 `Sub.V7`, `Sub.V7/II` … — **`7`만 작게**, `Sub.`은 로마숫자와 같은 크기 회색, 나머지는 큰 브랜드색(`_comboV2RomanHtml`).

**이론 제약: dim7은 대칭**이라 루트 반음 % 3이 같은 도미넌트끼리는 같은 코드다(C#dim7 = Edim7: A7·C7 / D#dim7 = F#dim7: B7·D7 / G#dim7 = Bdim7: E7·G7). 한 문제 안에 같은 묶음의 dim7을 정답·오답으로 같이 넣지 않는다.

**연결형** (왼쪽 = 도미넌트, 오른쪽 = 대리코드): 변형 3가지 랜덤.
- 도미넌트 ↔ 3도 위 dim7 (G7 ↔ Bdim7): "C key에서 도미넌트 코드와 / 3도 위 디미니쉬 코드를 짝지어 주세요"
- 도미넌트 1전위 ↔ 3도 위 dim7 (G7/B ↔ Bdim7): "C key에서 도미넌트 1전위 코드와 / 3도 위 디미니쉬 코드를 짝지어 주세요"
- 도미넌트 ↔ 트라이톤 대리 도미넌트 (A7 ↔ Eb7): "… / 트라이톤 대리 도미넌트 코드를 짝지어 주세요"
- dim7 짝은 묶음마다 하나씩 **항상 3개**, 서브 짝은 3개(70%) / 4개(30%).

**진행 문제(배치형·교체형·빈칸형)**: 진행은 **항상 8코드 진행**(챕터 5식 투-파이브, `%` 사용; 소스는 코드 반주 훈련 데이터 + 챕터 5 생성기). **대리코드는 한 마디를 온전히 쓰면 어색해서 짧게 건너가는 약박(반 마디의 뒤쪽 칸 = 짝수 번째 칸 2·4·6·8)에만 온다** — 투-파이브의 도미넌트 칸이 바로 그 자리. 대상 도미넌트는 묻는 투-파이브의 도미넌트(투-파이브가 2개인 진행에서는 하나만 바꾸고 나머지는 그대로).
- **교체형**: 도미넌트 칸(칩)을 대리코드로 교체. 정답 = 3도 위 dim7 또는 트라이톤 서브 중 하나(반반), 오답 2 = 다른 도미넌트의 대리코드(같은 도미넌트의 다른 대리코드·같은 묶음 dim7은 제외해 정답이 하나가 되게, 오답끼리 같은 묶음 dim7도 제외). "C key 코드진행에서 / **A7** 도미넌트 코드를 / 대리코드로 교체해주세요". 채점 후 정답 표기(`#Idim7` 등)가 칩 아래에 나옴.
- (보존, 미출제) 빈칸형: 도미넌트 칸을 비우고 아래 표기(`Sub.V7/II`, `#Idim7`)로 코드를 고름. "… / 빈칸에 알맞은 대리코드를 채워주세요".
- **배치형**: 대리코드 1개만 쓴 8코드 진행을 미리 계산. **`%`를 뺀 모든 칸이 빈칸**(투마이너·도미넌트·다이어토닉 코드 모두 배치, 5~6칸)이고 칸 아래 표기(`Rel.IIm →`, `V7/VI`, `Sub.V7/II` 등)를 보고 채움. **배치형은 한 판의 후반부에 나온다**(챕터 6 한정). 풀 = 정답 코드 전부 + 다이어토닉·도미넌트·dim7·서브 오답으로 채워 8개(2줄). "C key 코드진행에서 / 빈칸에 알맞은 코드를 배치해주세요".
- 반대(도수 찾기) 문제 없음. 진행 속 도미넌트 1전위는 나오지 않음(1전위는 연결형 전용).
- **1도(C)를 향하는 투-파이브(Dm7 G7 → C)는 진행 문제에서 제외**(그냥 다이어토닉 진행이라서, 2026-10-27). 프라이머리 도미넌트 G7 자체의 대리코드(Bdim7, Db7(#11))는 **연결형에서 그대로 유지**된다. 진행 문제의 대상 도미넌트는 세컨더리(V7/II~V7/VI)만 나온다.

### 7-6. 챕터 7 (텐션코드)

레벨 설정 `COMBO_V2_LEVELS['7-N']` = `{keys, kinds: 배치형·교체형, ch7: true, challenge?}`. 구조는 챕터 4~6과 같음(7-6 종합 = 키 레벨, 7-7~7-14 선택 구간 = 도전 레벨 `challenge: true`). **연결형·빈칸형·분류형은 출제하지 않는다**(연결형은 낼 거리가 없고, 빈칸형은 "텐션을 코드에 덧입힌다"는 주제와 안 맞고, 분류형은 이번엔 제외). 한 판 본 문제 10개(챕터 4~는 15개), 두 유형 3:2.

- **박자**: 4코드 진행은 **120BPM, 코드 하나 = 2박(1초)**(`COMBO_V2_PLAY_BPM` `COMBO_V2_PLAY_BEATS`), **8코드 진행은 90BPM, 칸 하나 = 1박(약 0.67초)**(`COMBO_V2_PLAY_BPM_8`; 4코드를 2배로 압축한 박자라 전체 길이가 4코드와 비슷). **`%` 칸은 새로 스트럼하지 않고 직전 코드를 그 칸만큼 이어서 울린다**.
- **코드 이름 해석** (`_comboV2ChordStep`): 루트·품질(`M m dim aug M7 7 m7 m7(b5) dim7 sus4 sus2 add9 6 m6 7sus4`)·슬래시 베이스(`/E` → 근음 기준 반음)·텐션 `(…)`(`Dm7(9)` → `m7` + `(9)`, `G7sus4(9)` → `7sus4` + `(9)`)로 나눈다. 해석 못 하는 표기가 하나라도 있으면 그 진행은 무음(조용히 반환).
- **이탈 처리 (CLAUDE.md 0-2)**: 문제 전환(`_comboV2QShow`)·화면 이탈(`comboV2ExitQuiz`: X·탑바 뒤로가기·Android 뒤로가기가 모두 이 함수)·`pagehide`·`visibilitychange(hidden)`에서 `_comboV2SoundStop()`이 **하드컷(`GuitarAudio.panic()`)** — 소프트 `stop()`은 예약된 스트럼이 남아서 쓰지 않는다. 스피커 재탭도 같은 정리 함수. 재생 준비(await) 중 정리되면 늦게 시작하지 않도록 세대 번호(`_comboV2Play.gen`) 가드. 정상 종료는 페이드로 끝나므로 상태만 되돌린다.
- **스피커 파동 애니메이션 (2026-10-28)**: 재생 여부와 상관없이 **항상** 아주 약하게 움직여 아이콘이 살아있다는 느낌만 준다 — 안쪽·바깥 소리 파동(아이콘의 마지막 두 path, `nth-last-of-type`)의 투명도만 2.4초 주기로 0.55↔1을 오가고 바깥쪽이 0.3초 늦다(CSS만, 이동·크기 변화 없음).
- **자동 재생 (2026-10-28)**: 소리가 있는 유형(배치형·교체형·빈칸형)은 문제가 표시되고 **0.25초 뒤 정답 진행을 자동으로 1회 재생**한다(`COMBO_V2_AUTOPLAY_MS`, `_comboV2QShow` 끝에서 예약). 오답풀이로 다시 나온 문제도 똑같이 1회 재생. 예약은 `_comboV2SoundStop`이 함께 취소하므로 문제 전환·이탈·`pagehide`·백그라운드에서 남지 않는다. 연결형·분류형은 소리 없음. 스피커를 누르면 다시 들을 수 있다(재생 중에 누르면 정지).
- 한 번만 들려주는 재생이라 `COMBO_V2_PLAY_PICK = {cyclic:false, topW:0.5, bassW:0.5}`로 보이싱을 고른다(아래).

### 8-2. 보이싱 선택 알고리즘 (`voicing-cycle.js`, `VoicingCycle.pick(steps, keyIdx, opts)`)
코드반주 훈련(`chordplay-practice.js` 855~943줄, `progression-detail.js`)의 순환 DP를 모듈로 옮기고 확장한 것. 후보는 `ProgressionVoicings.getCandidates`(허용 목록 통과분). steps = `[{root, quality, bass?, tension?}]`.
- **기본 규칙(코드반주와 동일)**: 첫 코드 = 최저 프렛 후보 고정 → 나머지는 이동 비용 최소 경로 → (cyclic이면) 마지막→첫 코드 이동 비용 포함. 비용 = 프렛 거리 + 근음 줄 변경 페널티(2) + 고프렛(5 초과, 프렛당 0.8) + 3번줄 이상 근음(2.5) + 4번줄 근음(2.5) − 0~1프렛 보너스(1.5) + ii→V 쉘 연결 보정(m7(b5) 6번줄 쉘 → V7이면 alt shape 가산). C·D·E·G·A key는 오픈 보이싱 1개 고정, 그 외 key는 정적+패턴 전부 후보.
- **병목 코드 규칙(2026-10-27)**: 진행 안에서 **가장 낮은 후보 프렛이 3프렛 이상인 코드**(오픈 포지션이 불가능한 코드, `BOTTLENECK_FRET`)가 있으면, 그 코드를 최저 프렛 후보로 고정하고 **다른 코드도 3~6프렛대 보이싱을 쓴다** — key별 오픈 고정을 풀고(정적+패턴 전부 후보), **개방현을 쓰는 보이싱은 후보에서 뺀다**(후보가 모두 개방현이면 그대로 둠). 예: `Dm7 G7(13) CM7 A7` → `x 5 7 5 6 5` / `3 5 3 4 5 3` / `x 3 5 4 5 3` / `5 7 5 6 5 5`.
- **퀴즈 재생 옵션**: `cyclic:false`(한 번 재생이라 마지막→첫 코드 비용 없음, 병목 코드를 고정하고 앞뒤로 뻗는 두 사슬) + **탑노트·베이스(최저음) 이동 가중**(반음당 0.5). 검증 예: `CM7 A7(b9) Dm7 G7` → `x 3 5 4 5 3` / `5 x 5 6 5 6` / `x 5 7 5 6 5` / `x x 5 7 6 7`. 코드반주 훈련은 기본값(순환, 가중 0) 그대로.
- 12key 스캔(메이저 진행 59개 × 변형 708케이스 × 12key): 후보 없는 진행 0건. 의심 진행(이웃 프렛 도약 5 이상·진행 프렛 폭 6 이상·최고 프렛 9 이상)은 챕터 1·2에서 거의 없고 챕터 7 텐션에서 약 90건 — 주로 `M7(13)`처럼 낮은 프렛 보이싱이 없는 텐션.

### 8-3. 라이브러리·허용 목록 규칙 (`chord-voicings.js` → `chords-library.js` → `progression-voicing-list.js`)
- **코드진행에 쓰이려면 두 곳을 통과해야 한다**: ① `chord-voicings.js`의 정적/패턴 보이싱(코드 사전에도 같은 데이터가 나온다) ② `progression-voicing-list.js`의 허용 목록(정적은 fret 배열 exact match, 패턴은 **최저 프렛 기준 상대 shape**). 라이브러리에만 있고 허용 목록에 없으면 **후보에서 조용히 빠진다** — 이 불일치가 낮은 프렛 보이싱 누락의 주원인이었다.
- **점검법**: 라이브러리 텐션 패턴을 전부 shape로 바꿔 허용 목록과 대조(41종 전부 통과 확인). 새 패턴을 넣을 때는 (1) 패턴을 `chord-voicings.js`에, (2) 같은 shape를 허용 목록에 함께 추가한다. 슬래시·텐션 허용 shape는 복사 오류(`7(#9)` shape를 `7(13)`·`7(#11)`에 중복 기재)가 있었으니 새로 쓸 때 canvas 순서(1→6번줄)·최저 프렛 정규화를 확인.
- **2026-10-27 추가·수정**:
  - 트라이어드 M·m **4번줄 근음** 허용(`x x r r+2 r+3 r+2` / `x x r r+2 r+3 r+1`): Eb `x x 1 3 4 3`, Ebm `x x 1 3 4 2` 등 → Eb·Ebm 최저 프렛 8 → 4.
  - **add9 패턴**(5번줄 근음 없음): 6번줄 `r+1 x r+3 r+2 r+1 r+3`(운지 `T x 3 2 1 4`, 예 Gb `2 x 4 3 2 4`), 4번줄 `x x r+2 r+1 r r+2`(운지 `x x 3 2 1 4`). 정적 add9(`Cadd9 ×2`, `Gadd9 ×2`, `Aadd9 x02420`)을 허용 목록에 추가. `Eadd9`(`0 2 4 1 0 0`)의 품질 오기(`m`)를 `add9`로 수정.
  - **7(13)**: 6번줄 패턴2 `r+1 x r+1 r+2 r+3 x`(운지 `1 x 2 3 4 x`, 예 G `3 x 3 4 5 x`) 추가 + 패턴1(`3 5 3 4 5 3`)의 허용 shape 복구. **7(#11)** 5번줄 shape `[null,2,0,1,0,null]` 허용.
  - **슬래시 M7**: `FM7/A` 드롭3 `r+2 x r r+2 r+2 x`(운지 `2 x 1 3 4 x`, 예 `5 x 3 5 5 x`), `CM7/E` 드롭2,4 `x r r+2 x r+1 r+1`(운지 `x 1 4 x 2 3`, 예 `x 7 9 x 8 8`) 추가 + 허용.
- **12key 보이싱 현황(챕터 1~9 코드 종류 기준)**: M·m·dim·M7·7·m7·m7(b5)·dim7·m6·sus2·sus4·add9·1전위(`M/3` `M7/3` `7/3`)·텐션 11종(M7(9)·(13)·(#11), m7(9)·(11), 7(9)·(13)·(b9)·(b13)·(#11), 7sus4(9))는 12개 root 전부에 후보가 있다. 단 일부는 높은 프렛만 있다(`add9` Db·D·Eb 9~11프렛, `7(13)` G·Ab 근처 10~11프렛, `M7(13)` D·Eb 5~6프렛, `m7(b5)` D 5프렛) — 챕터 3은 7프렛 이하 필터로 출제에서 제외하고 챕터 7은 병목 코드 규칙으로 연결한다.

## 10. 미니강의 (모션그래픽 강의, 2026-10-28~29 챕터 1~6 구현)

### 10-2. 진행 규칙 (엔진이 이미 구현 — 새 챕터는 건드릴 필요 없음)
- 단계(step)를 **묶음(group)** 으로 나눠 "다음" 버튼은 묶음의 마지막 단계가 끝나야 켜지고, 묶음 안 단계는 앞 단계가 끝나면 버튼 없이 자동으로 이어진다. 마지막 묶음의 버튼은 "완료".
- **항상 문구가 먼저**: 문구를 띄우고 `CAPTION_LEAD_MS`(1초) 뒤에 연출·소리 시작(동시에 시작하면 눈이 둘 다 못 따라감). 단계마다 최소 `MIN_STEP_MS`(2초) 후에 다음으로. 연출이 끝나야 하고(`run()`이 약속을 돌려줌), 20초 넘게 안 끝나면 포기하고 진행(`STEP_FAILSAFE_MS`).
- **문구 사이 최소 간격(2026-10-29, 챕터 5 작업 중 추가)**: `CAPTION_GAP_MIN_MS`(3초) — 문구가 뜬 뒤 **같은 묶음의 다음 문구가 뜨기까지**, 그리고 묶음 끝의 "다음"이 켜지기까지 이 시간보다 짧아지지 않는다(문구가 있는 단계만, 빈 문구 단계는 제외). 새 챕터·새 단계에 자동 적용되니 단계마다 늦추지 말 것. 너무 빠르면 이 값만 키운다(5초·4초는 사용자가 길다고 해서 3초로 정함). 한 단계 안에서 `showCaption`을 직접 부르는 챕터 1 첫 단계도 이 값을 따른다(`SHOW_MS`). 챕터 1~4에도 같이 적용됨 — 가상 시계 기준 총 길이 1장 61→67초, 2장 68→71초, 3장 137→139초, 4장 185→193초, 5장 131→137초, 6장 192초(버튼 즉시 클릭 기준).
- **문구 자리는 3줄 고정(2026-10-29)**: `.combo-v2-lec .combo-v2-lec-text`의 `min-height`가 3줄, 글자는 맨 위부터(`align-items: flex-start`), 아래 여백 16px. 문구가 2줄↔3줄로 바뀌어도 가운데 정렬된 문구+무대 블록의 높이가 같아 **아래 연출 위치가 안 움직인다**. 2줄 문구와 무대 사이 = 빈 셋째 줄 + 16px ≈ 예전 40px.
- 묶음의 마지막 단계가 **소리**를 낼 때는 `STEPS_CHn[i].ms`(단계 시작 기준 소리 꼬리까지의 시간)를 반드시 지정 — 연출 코드가 오류로 일찍 끝나도 그 전엔 "다음"이 안 켜짐.
- "다음" 버튼은 **활성/비활성 둘뿐**(hover 색 없음). 켜는 길은 `setNext(false)` 하나, 묶음이 시작되면 무조건 비활성, 감시 타이머(`startWatch`)와 `aria-disabled`로 이중 방어. 버튼 CSS는 **ID 선택자**(`#combo-v2-lec-next`) — 예전에 마크업에 없는 클래스를 CSS가 가리켜서 한 줄도 안 먹은 사고가 있었음.
- **이탈(CLAUDE.md 0-2)**: X·Android 뒤로가기는 확인 모달(`showLeavePracticeModal`) 뒤 `abort()`, 홈/앱 전환(`visibilitychange`)·`pagehide`는 확인 없이 `abort()`. `abort()`는 하드컷(`GuitarAudio.panic()`·`resetPiano()`)+타이머·애니메이션 취소+화면 초기화, 늦은 콜백은 세대 번호(`L.tok`/`L.gen`)로 차단. 정책은 "처음부터", **수강 완료는 마지막 "완료"를 눌렀을 때만** 기록.
- 해금: 강의를 볼 권한 = `chapterOpen(n)`(1장 또는 이전 챕터 키 레벨 클리어), **강의를 끝까지 봐야 그 챕터 첫 레벨이 열림**. 건너뛰기 테스트 통과·더 높은 챕터로 건너뛰면 낮은 챕터 강의는 본 것으로 간주(다시 볼 수는 있음, 이때 완료 페이지 없이 목록으로).
- 첫 접속 시작 페이지(`maybeShowWelcome`): 이 훈련에 처음 들어왔고 1장 강의를 안 봤으면 한 번만(보인 시점에 `_welcome` 기록). 힌트 파동(`_comboV2UpdateHint`): 열린 가장 높은 챕터의 ▶(강의 안 봤으면) 또는 풀 수 있는 가장 높은 레벨 도넛에, 그 모양 그대로 복제한 SVG가 4px 정도 퍼졌다 사라짐. 마지막 레벨까지 클리어하면 없음.

### 10-3. 새 챕터 강의 만드는 순서 (체크리스트)
1. **기획(CLAUDE.md 0-5)**: 단계마다 "유저가 이 순간 얻어야 할 핵심"을 표로 적어 승인받는다(표에 "핵심" 열). 강의의 **최종 목적(유저가 결국 외우고 써야 할 것)** 에서 거꾸로 따진다. 판단이 안 서면 구현 전에 사용자에게 묻는다. 단계는 세분화하되 "다음" 묶음은 따로 정한다.
2. **문구**: 줄당 약 20자(캡션 폭 328px = 360px − 좌우 인셋 32px, 18px 기준) 이하 + 보통 2줄(`\n`), 넘으면 **3줄로 나누고 키워드에 강조**(문구 자리가 3줄 고정이라 3줄이어도 무대는 안 움직임). 강조는 따옴표 대신 `em('…')`(파랑). 해요체. 공통 마무리는 `endingStep(n)`(챕터 번호만 바뀜).
3. `STEPS_CHn` 작성(`{ text, run }`, `run()`은 끝나면 풀리는 약속) → `GROUPS_CHn`(단계 번호 0부터) → 소리 있는 묶음 끝 단계에 `.ms` → `LECTURES[n]`에 등록.
4. 무대: 챕터 1 무대(`buildStage`)로 충분하면 그대로, 다르면 `buildStageN()`을 만들고 `open()`의 분기(`if (n === 5) buildStage5(); else if (n === 4) buildStage4(); else if (n === 3) buildStage3(); else if (n === 2) buildStage2(); else buildStage();`)와 `resetView()`의 클래스 제거(`is-ch2 is-ch3 is-ch4 is-ch5`)에 추가. 층을 겹치는 방식(챕터 3·4)은 `.lec3-l` 레이어 + `layer4(id)`처럼 한 번에 한 층만 켜는 함수를 둔다(챕터 5도 `layer4`를 그대로 씀).
   단계 옵션: `enter`(문구가 뜰 때 곧바로 앞 장면을 치움), `seq: true`(문구를 한 줄씩 차례로), `text: ''`(문구 없이 장면만 — 앞 문구가 먼저 사라지고, 다음 단계에서 문구가 뜸).
5. `chord-combo.js`의 `COMBO_V2_LECTURE_READY`에 n 추가, `COMBO_V2_CH_COLORS`는 이미 9색이 있음.
6. 검증: 문법 검사 + **가상 시계 시뮬레이션**(가짜 DOM + 가상 타이머로 엔진을 실제로 돌려 묶음 수·활성화 시각·오류·소리 횟수 확인, 연타 억지 테스트 포함 — 만든 하니스는 프로젝트 밖 임시 폴더라 필요하면 다시 만든다). **시뮬레이션은 DOM 클래스만 보고 렌더링은 못 본다** → 위치·색·겹침은 CSS·마크업을 읽어서 확인하고 사용자 기기 확인 전엔 "미확인"이라고 보고(CLAUDE.md 0-1 "화면 요소 추가·수정 전 확인").

### 10-6d. 작은별 악보 (챕터 3~6 공통, 2026-10-29 확정·구현)
챕터 3부터 작은별 진행은 칸 격자가 아니라 **진짜 악보처럼** 보여준다(챕터 1·2는 예전 칸 격자 그대로). 사용자가 목업(미리보기)으로 모양을 확정했고, 기기에서 보고 선 두께·색·글자 크기·간격을 고쳤다. 새 챕터에서 작은별을 쓰면 이 방식을 따른다.

### 10-7. 디자인 원칙·교훈 (챕터 3 이후에도 지킬 것)
- **핵심 위계**: 외울 대상(코드 이름·도수·기능 이름)이 크고 진하게(`--type-title-lg`), 과정(음이름)은 작고 회색, 지금 핵심만 파랑(`.is-focus`). 위에서 아래로 중요한 순서(이름 → 도수 → 음). 이름은 로마자와 달리 m·dim 같은 품질도 근음과 같은 크기.
- **위치는 안 움직인다**: 그 단계가 끝났을 때 보이는 구성의 자리를 처음부터 잡아 두고(다음 단계에 나올 것의 자리는 미리 비우지 않음 — 지금 화면의 균형이 우선, `docs/chord-combo-lecture-style.md` §0) 요소는 투명도·색으로만 등장·강조·교체. 의도된 이동은 "핵심이 바뀌는 순간"에만(챕터 1 5단계의 열 벌어짐, 챕터 2의 두 줄 이동·복사 이동·층 전환).
- **카드·박스 금지**(style-guide §0): 간격·크기·색으로만 묶는다. 하얀 그라디언트 같은 가림막은 **자기 단계 전에는 안 보이게 컨테이너 투명도부터** 제어(안쪽 글자만 투명하면 배경이 처음부터 보임 — 챕터 2에서 실제로 난 사고).
- **파랑 = 지금 핵심**. 챕터 2에서 해결 색이 파랑이라 겹치므로, 기능 색을 쓰는 화면에서는 파랑 강조를 빼고 투명도(흐리게/진하게)로 강조한다.
- **7th 이름은 한 칸(360px에서 약 47px)에 안 들어간다**(`Bm7(b5)` 약 59px, `VIIm7(b5)` 약 63px 추정): 한 줄 7열이면 `Am7`과 `Bm7(b5)`가 1px 간격으로 붙는다. 해법 = 위 4개(80px 간격) + 아래 3개(글자 폭을 재서 여백 같게, 줄 가운데) 두 줄 배치. 7th가 아닌 챕터는 한 줄 격자 그대로.
- **줄별 등간격은 시도했다가 폐기**(2026-10-28): 한 열의 이름·도수는 폭이 달라서 줄마다 여백을 같게 맞추면 이름과 도수가 세로로 어긋나고, 앞으로 바뀔 글자의 최대 폭으로 잡으면 지금 글자 기준 여백이 제각각이 된다. 기본은 **열 가운데를 같은 간격**(7칸 격자).
- 괄호 표기 `(b5)`는 항상 위첨자: 이름은 `_ccFormatB5(text)`, 도수는 `.lec-rq .cc-sup`(11px 하한). 한 덩어리 `span`으로 감싸야 flex 안에서 위첨자가 올라간다.
- **flex 부모 주의**: 캡션 박스(`.test-question-text`)는 `display:flex`라 안에 span이 섞이면 칸으로 갈라진다 → 캡션 전체를 `<span class="lec-cap">` 하나로 감싸 넣는다(`showCaption`).
- **소리**: 기타는 컴프레서를 거쳐 벨로시티로는 안 줄어들어서 동요 같은 균형은 **컴프레서 뒤 트림**(`setOutputTrim`)+피아노 게인으로. 화면 연출은 소리보다 약 100ms 빠르므로 `LEAD_MS`(= 예약 지연 + Tone lookAhead)만큼 늦춰 맞춤. 음을 이어 칠 땐 레가토(다음 음이 시작될 때까지 울리고 짧게 페이드).
- **스타일 가이드 토큰만**: 새 색 금지. 기능 색은 `--blue`·`--icon-purple`·`--icon-coral`(노랑은 흰 배경에서 글자로 안 읽혀 제외). 여백은 4px 배수 토큰.
- 무대 높이는 가장 큰 화면(챕터 2는 분류판 층 220px)에 고정하고 위쪽 정렬 — 단계가 바뀌어도 아래 버튼·캡션이 안 움직임. 360×640에서 캡션(약 88px) + 무대 + 버튼이 한 화면에 들어가는지 확인.
- **강조는 아껴 쓴다(챕터 4에서 사용자가 반복 지적)**: 문구의 강조는 사용자가 대괄호로 지정한 말만, 무대의 파랑·코랄은 그 단계의 핵심 하나에만. 이름표("도미넌트"·"논-다이어토닉 코드")나 바뀐 코드 이름 전체에는 강조색을 쓰지 않는다(바뀐 음만). 모든 단계에 옅게/파랑을 습관적으로 걸지 않는다.
- **문구는 앞 문장을 받아야 한다(챕터 4에서 반복 지적)**: 주어를 생략하지 말고, 처음 나오는 용어(해결음·도미넌트·타겟 등)는 정의한 뒤에 쓰며, 다음 장면으로 점프하기 전에 연결 문장을 둔다. 문구를 새로 쓸 때 "앞 문장 → 이 문장"이 이어지는지 먼저 확인.
- **한 표기 안에서 글자 크기를 섞지 않는다**: `V7/II`를 V·II는 크게, 7·/는 작게 섞으면 어색하다(퀴즈 카드의 도수 표기 규칙을 그대로 가져온 것이 문제). 강의의 큰 예시는 한 크기·한 색으로, 설명하는 부분만 색으로 구분.
- **열 폭이 다른 두 줄을 한 격자에 넣을 때**: 아래 줄 글자가 위 줄보다 넓으면 열이 벌어져 위 줄 기호(슬래시) 앞뒤 여백이 넓어진다 → 아래 줄 칸 폭을 0으로 두고(가운데 정렬 오버플로) 위 줄만으로 열 폭을 정한다(챕터 4 `V7/II` 예시).
- 소리 시작 규칙(챕터 3 방식 유지): 화면 변화(이름·음)가 끝난 뒤 소리를 낸다. 스케일은 1장과 같은 레가토(음 길이 = 간격, 0.18초 페이드).
- **진행은 시간 순서대로 왼쪽→오른쪽(챕터 5)**: 실제 코드진행이 좌→우로 흐르므로 표도 한 줄 = 한 진행(`Rel.IIm · 세컨더리 · 타겟`)으로 쌓는다. 타겟 위·친구 아래로 가로 열을 나열하면 5열 폭이 모자랐다(`F#m7(b5)` 약 72px). 칸 폭은 줄마다 같게 고정(80/40/56px, 칸 사이 24px)해 세로로 정렬하고 목록 장면도 같은 폭을 쓴다. 5줄+이름표는 무대 220px 안에 들어가야 해서 위 여백 16px·줄 간격 8px(약 206px).
- **한 개념의 예시 진행은 연속 단계에서 통일(챕터 5)**: 꺾쇠·표기·바꿔 쓰기·박자 쪼개기를 모두 `Gm7 C7 FM7`(FM7 줄)로 — 챕터 4가 `Dm7·A7`을 이어 쓴 것과 같다. 문구에 쓴 예시와 장면의 예시가 다르면 문구를 장면에 맞춘다.
- **3줄 문구는 키워드에 강조(챕터 5)**: 줄이 길어 3줄로 나눈 문구는 시선이 흩어지므로 핵심 한 단어에만 `em`을 건다(`[2도 마이너]`, `[논-다이어토닉]`, `[변형]`). 2줄 문구는 종전대로 용어 한 단어.
- **문구 폭 점검(챕터 5)**: 문구가 캡션 폭 328px(360px − 좌우 인셋 32px)에 들어가는지 글자 폭 추정으로 먼저 확인한다(한글 16.4~18px, 숫자 11px, 영문 대문자 12px·소문자 10.5px, 공백 4px, 자간 -0.04em). 경계선(±2%) 문구는 기기에서 확인. 문구는 `lec-cap`이 한 덩어리로 접히므로 한 줄이 328px를 넘으면 그 줄만 접혀 줄 수가 늘어난다.
- **지금 보이는 그 시점의 시각적 밸런스(6장, 재발 방지 규칙)**: 다음 단계에 나올 것의 자리를 미리 비워 두지 않는다 — 6장 표 범례에서 25번에 나올 '서브' 자리를 미리 잡아 14번의 범례 5개가 왼쪽으로 쏠렸다. 나올 것은 자리를 차지하지 않게 두고(`lc6-off`) 나올 때 기존 요소를 새 균형으로 미끄러뜨린다(`slideIn`). 같은 단계 안에서 나타날 것의 자리를 미리 잡는 건 허용. 자세한 건 `docs/chord-combo-lecture-style.md` §0.
- **표의 축은 기획 때 확인(6장)**: 열이 무엇이고 줄이 무엇인지를 단계표 승인 때 적는다(6장은 처음 줄 = 도미넌트로 짜서 반전시킴).
- **표가 무대보다 넓으면 통째로 scale(6장)**: 6열 폭이 약 380px이라 `fitTable`이 약 0.87배로 줄임(글자 약 12px). 열 폭은 가장 넓은 칸에 맞춰 같게, 범례는 표 밖이라 안 줄어듦.
- **운지는 구성음을 계산해 검증(6장)**: 사용자가 준 `FM7 x x 1 3 3 3`은 D# A# D G라 FM7이 아니었다. 구현 전에 확인한다.
- **느린 애니메이션은 완성 순간에만(6장)**: Db7 완성(새 음 1초, 이름 500/700ms) — 평소 속도(0.4초)와 대비되어 "중요하다"는 신호가 된다. 남발하면 의미가 사라진다.
- **문구 → 연출 → 완료 문구(6장)**: 질문 문구 뒤 연출이 답을 먼저 보여 주고, 완료 문구는 다음 단계로 분리한다.
- **같은 용어를 한 문구에서 두 번 강조하지 않는다(6장)**: 첫 줄의 `트라이톤`은 강조 없이, 둘째 줄의 이름에만.

### 10-8. 미정·확인 필요 (챕터 1·2·4·5·6 공통)
- **기기 미확인**: 챕터 2의 두 줄 배치 간격·복사 이동 경로·Em/G 비교 그라디언트·기능 색 대비·360px에서 `VIIm7(b5)` 도수 폭. 소리 균형(작은별, 7th 재생)과 모든 연출의 체감 속도.
- **챕터 4 기기 미확인**: 7th 코드 두 줄 배치(위 4·아래 3) 아래에 도미넌트가 붙은 간격, 5열 표(`V7/III` 18px 폭)·5개 코드+세컨더리 배치, `V7/II` 큰 예시와 슬래시 간격, 끝 목록의 `…` 위치, 문구 줄바꿈(한 줄 25자 넘는 문구가 여럿 — 3줄로 넘어갈 수 있음), 한 줄씩 뜨는 문구의 템포, Cm7·세컨더리 운지의 청감, 코랄·파랑 대비. 문구를 아직 고치는 중(사용자가 단계별로 수정).
- **챕터 4 미정**: 7번 "Cm7로도 해결 — 이유는 나중에"의 설명 위치(이후 챕터), 25번과 끝 장면(36번)이 비슷한 화면이라 반복처럼 느껴지는지.
- **챕터 5 기기 미확인**: 세컨더리·타겟 5줄이 가운데에 뜬 뒤 오른쪽으로 밀려 자리를 잡는 정렬(밀기 거리 52px은 `.lec5-kc` 칸 폭과 짝), 5줄+이름표 높이(계산상 약 206px/220px), 꺾쇠 양 끝(Gm7 가운데~C7 가운데)과 선·글자 간격 4px, 쪼갠 칸 시연(19번)의 정렬(1.5배 폭)과 C7이 밀리는 연출, 새 보이싱의 청감(위 10-6c ①), 문구 3줄 자리 고정 뒤의 문구–무대 간격(3줄 문구는 16px), 문구 최소 3초가 읽기에 충분한지(전 챕터에 적용됨).
- **작은별 악보 기기 미확인(챕터 3~5)**: 양끝 세로선 두께가 같게 보이는지(2px 정수 맞춤), 회색 선·18px 코드·16px 가사의 가독성, 코드·가사와 가로선 사이 간격(약 4px), 악보가 무대 위쪽에 붙고 아래 약 76px이 비어 보이는지(가운데로 내릴지 결정), 5장 `Bm7(b5)`→E7→Am7 밀림과 오른쪽 세로선 여유, Rel.IIm이 열릴 때 C7·E7이 1박 뒤로 밀리는 연출, 태블릿(코드 20px)에서의 폭, 가사 층이 악보 위에 정확히 겹치는지.
- **챕터 5 경계선 문구**: 3번("2-5-1 진행은 아주 많이 사용되는 진행이에요" 약 323px)·25번("높은 수준으로 연주하고 분석할 수 있게 돼요!" 약 322px)은 한글을 1em으로 잡으면 3줄이 된다(캡션 폭 328px). 기기에서 접히면 한두 단어를 줄일 것. 챕터 3 패싱코드 문구·챕터 4 마지막 문구도 같은 이유로 3줄로 접힐 수 있음(문구 자리 3줄 고정이라 무대는 안 움직임).
- **챕터 5 미정**: 훈련 안내 단계 없음(필요하면 25~27번 뒤에 추가). 시연(19번)은 쪼갤 칸이 처음부터 넓어서 쪼개기 전에도 칸 폭이 약간 불균등함(악보는 해당 없음). 3번 문구는 사용자가 "이예요"로 적어 "이에요"로, "작.편곡"은 "작·편곡"으로 고침.
- 수강 완료(`_lec`)는 서버에 안 올라감(기기를 바꾸면 사라짐) — 서버 저장은 SQL 작성 승인 후.
- 강의 문구의 번역(en/ja/es)은 아직 없음. "수고하셨습니다!"(합쇼체)는 다른 문구(해요체)와 톤이 다름 — 공통 마무리라 바꾸려면 `endingStep` 한 곳.
- 강의 다시 보기 진입 경로는 ▶ 버튼뿐. 위 한 줄 7th를 두 줄로 옮기는 연출을 뺄지(한 줄 등간격으로 충분한지)는 기기 확인 뒤 결정.
- **챕터 6 기기 미확인**: 표 6열이 360px에서 한 화면에 들어가는지(scale 약 0.87배, 글자 약 12px)와 높이(약 216px/220px), 줄 색 대비(분홍·초록), 범례 위치(표 아래 24px)와 서브 줄이 더해질 때 범례가 미끄러져 재배치되는 모양, 악보 아래 줄 코드 7개의 글자 축소(`--sc-fs`)와 마디선에 걸치는 코드, 5번 칸 `CM7 Am7` 간격, 27번에서 Gm7이 사라지며 Em7(b5)가 자리를 차지하는 연출, 트라이톤 세로 괄호·이름표 위치, B·F 자리 맞바꿈, Db7이 느리게 완성되는 체감, 한국어 문구 아래 영어 라벨(`Tritone`·`Substitute`)이 겹치지 않는지(문구 첫 줄 약 312px 경계선), 지정 운지의 청감.
- **챕터 6 문구 경계선**: 16번 첫 줄(약 324px), 23·24·25번이 기기에서 접힐 수 있다(문구 자리 3줄 고정이라 무대는 안 움직임, 단 영어 라벨이 붙는 23번은 2줄이어야 라벨이 안 겹침).
- **챕터 6 미정**: 퀴즈 카드의 `#Idim7` 같은 dim7 도수 표기는 강의에서 설명하지 않음(표기는 `Sub.V7/II`만), 일본어판 영어 라벨 방식, 표의 서브 열 이름 `서브`가 적당한지, 5장 문구(`m7(b5)`)가 일반 글자인 것과 6장(위첨자)의 불일치.

### 10-9. 강의 공통 패턴 (챕터 1~6 통합, 2026-10-29) — 새 챕터를 기획할 때 먼저 읽을 것(상세한 스타일 가이드는 `docs/chord-combo-lecture-style.md`)
챕터 1~4를 분석한 패턴에 챕터 5·6에서 새로 생긴 것(5장·6장 표시)을 합친 것. 위 10-2~10-8의 개별 규칙을 새 챕터 관점에서 다시 묶었다.

**문구 스타일**
- 두 줄 구조: 1줄 = 앞 맥락·원인, 2줄 = 결론·새 개념, 줄바꿈은 의미 단위에서. 해요체, 용어 소개는 "~라고 해요/불러요", 소리 직전은 "~들어볼까요?/해볼게요!". 앞 문장을 받는 연결어(그래서·그런데·이렇게·하지만·또·그리고·말하자면)로 시작.
- 질문 → 답(5장): "~지 않을까요?"로 묻고 다음 단계가 "맞아요!"로 받는다. 복습 도입(5장): "N장에서 ~에 대해 배웠었죠!"로 앞 챕터를 떠올리게 시작.
- 한 문장의 조건이 둘이면(메이저일 때 / 마이너일 때) 별개 단계로 나누고 각각 자기 장면을 붙인다(5장). 용어는 풀네임 → 약어를 같은 자리에서 교체(5장, 이름표에는 강조색 없음).
- 강조: 사용자가 괄호로 지정한 용어·핵심 한 단어만 파랑. 라벨 태그·코드명 전체에는 쓰지 않고, 코랄은 긴장음에만. 3줄 문구는 키워드에 강조(5장).
- 줄 길이는 약 20자 이하(328px), 넘으면 3줄로 나눔(5장). 마무리: 소감(한 줄씩) → 의미 → 활용 → 공통 마무리. 훈련 안내 단계는 챕터 1~4에만 있고 5장은 생략.
- 사용자 표기 약속(5장): `/` = 줄바꿈, `->` = 별개 단계, "(순서대로 나열)" = `seq`(한 줄씩).

**호흡**
- 문구가 먼저 뜨고(0.5초) 1초 뒤 연출·소리 시작, 단계 사이 자동 진행 간격 0.4초. **문구 사이 최소 3초(`CAPTION_GAP_MIN_MS`, 엔진 규칙, 5장 작업 중 추가)** — 묶음 끝의 "다음"도 그 뒤에 켜짐.
- 장면 → 문구 → 문구: 같은 장면 위에 문구만 있는 단계(`textOnly`)를 2~3개 연달아 얹어 의미를 풀어줌. `seq: true`는 소감·여운·마무리에만, 정보·논리 문구는 두 줄을 한 번에.
- 빈 문구 단계(`text: ''`)는 목록·총정리처럼 장면이 본체일 때, `enter`는 장면 전환 때 앞 장면을 즉시 지울 때. 묶음은 1~5단계, "소개 → 시연 → 해석" 한 덩어리.

**연출·소리와 문구의 연계**
- 단계 하나 = 변화 하나(문구가 말하는 새 변화와 장면의 변화가 1:1). 소리는 화면이 바뀐 뒤(`SETTLE_MS`), 울리는 것만 파랑·나머지 옅게(`LEAD_MS`로 화면 지연 보정). 마지막 코드는 길게(1.4~1.9초).
- 위계: 외울 것(코드명·도수) title-lg, 과정(음) title, 큰 예시 display-sm, 한 표기 안에서 글자 크기를 섞지 않음. 색 의미 고정: 파랑 = 지금 핵심·바뀐 것, 코랄 = 긴장, `is-dim`(0.3)·`is-faint`(0.12) = 지나간 것, 옅은 회색 = 안 울리는 것. 카드·박스 금지.
- 움직임에는 의미를 담음: 교체 `swap`, 음 이동 `rollNote`·`spin`, 배치 변경 FLIP(`regroupRows`·`openSplit`), 갈라짐·복사 이동. 의미 없으면 페이드.
- 작은별: 챕터 1은 원곡, 2~4는 원곡 → 리하모니(3장부터는 악보 모양, §10-6d), **5장은 앞 챕터(4장) 결과를 출발점으로** 삼고 바뀐 칸만 파랑. 박자를 쪼갠 칸은 1박씩 재생(5장).
- 예시 진행은 연속 단계에서 통일(4장 `Dm7·A7`, 5장 `Gm7 C7 FM7`). 소리 비교(5장): 같은 줄을 재생 → 이름 하나만 교체 → 다시 재생 → 원래대로.
- 줄 단위 강조(5장): 예시 줄만 진하게 → 대조할 줄 여럿만 진하게(줄 전체 투명도).
- 확장 연출 "민 다음 생성"(5장): 기존 것을 가운데에 한꺼번에 띄우고, 전체를 밀어 자리를 연 뒤 새것을 차례로 생성(친구의 친구).
- 꺾쇠(5장): 글자 폭을 재서 가운데~가운데 선 → 우리 표기(`Rel.II →`)로 교체(4장 `V7/II`와 같은 5부분 그리드, 아래 줄 폭 0). 목록(5장): 화살표 없이, 줄 안은 한 번에, 줄 사이 0.15초(4장은 화살표 있고 0.45초).

**배치·정렬**
- 세로: 문구(위, 가운데 정렬, **3줄 자리 고정·맨 위 정렬, 아래 여백 16px**) → 무대(최대 420px, 높이 220px 고정) → 버튼. 같은 묶음 간격 4px, 다른 묶음 32px.
- 진행은 시간 순서대로 왼쪽→오른쪽, 표는 세로로 쌓음(5장). 칸 폭은 줄마다 고정(80/40/56px)하고 표·목록이 같은 폭을 씀. 높이 예산 확인(5줄+이름표 ≈ 206px).
- 자리는 처음부터 잡고 투명도로만 등장. 쪼갤 칸 시연은 넓이를 미리 잡음(5장). 7th 7개는 위 4·아래 3.
- 작은별 진행은 **악보**(3장부터, §10-6d): 가로선 위 코드(칸 시작 박에 왼쪽 정렬, 겹치면 밀어냄)·아래 가사(마디 단위 왼쪽 정렬), 선은 회색 2px, 코드·가사는 가로선 바로 옆.

**6장에서 새로 생긴 것**
- 문구: 궁금하게(말줄임) → 연출로 답 → 완료 문구는 다음 단계, 부담 덜기("꽤 어려운 부분이에요 / 하지만 요령이 있어요!"), 조심시키기로 마무리, 같은 용어 중복 강조 금지, 한국어 낱말 아래 영어 라벨(마지막 줄에만, 번역판은 라벨 없음·스페인어는 영어 이탤릭).
- 연출: 구성음 비교 위젯 재사용(겹치는 음 파랑), 코드 하나가 둘로 갈라짐(Bdim → Bdim7·Bm7(b5)), 두 음의 자리 맞바꿈(FLIP), 느린 완성(`slowSwap`), 세로 괄호(`placeTritone`), 설명하는 음만 재생(B·F), 바꾸기 전 진행은 소리 없이 띄우고 바뀐 것만 재생, 새 요소가 생기면 기존 요소를 미끄러뜨려 재배치(`slideIn`·`reflowScore`).
- 배치: 행렬 표(열 = 다이어토닉 코드, 줄 = 종류) + 열 폭 통일 + 통째 scale + 줄 색 + 표 밖 범례, **지금 보이는 시점의 밸런스 우선**(다음에 나올 것의 자리를 미리 비우지 않음).
- 작은별: 5장 결과에서 출발해 바뀐 곳을 한꺼번에 바꾼 뒤 악보 순서대로 하나씩 짚음, 기반 진행 변경(`Dm7 - CM7 Am7`)은 4·5·6장에 일괄 반영, 코드가 많은 줄은 글자만 축소.
- 협업: 번호 흐름 → 문구 초안 단계표(줄 접힘 점검) → 번호별 문구 확정 → 지정 운지 목록 받기(구성음 검증) → 구현 → 소소한 수정 하나씩 반영 + 시뮬레이션 재실행.

**협업 규칙**
- 단계표에 "핵심" 열을 넣어 승인받고(CLAUDE.md 0-5), 문구는 사용자가 직접 고치며, 강조는 괄호로 지정한 곳에만.
- 사용자가 지정하는 값(운지·예시 진행)이 내 계산보다 우선(5장). 같은 문제가 반복되면 개별 수정 대신 엔진 규칙으로(문구 최소 간격·3줄 자리 고정, 5장).
- 시뮬레이션(가상 시계, `CH` 환경변수로 챕터 선택)으로 묶음 수·간격·오류를 확인하고, 렌더링은 기기 확인 전까지 "미확인"으로 보고.
