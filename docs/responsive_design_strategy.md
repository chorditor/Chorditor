# 반응형 디자인 전략 (모바일/태블릿/폴더블/데스크탑)

> 2026-08-11 최종 확정. 실기기 스펙 기반으로 전면 재작업 완료 — 과거 추정치·논의 과정은 삭제하고 확정값만 기록.

## 0. 최우선 원칙 — 화면이 코드와 모순되면 항상 내 코드를 의심

**사용자는 항상 하드리로딩(캐시 무시)해서 테스트한다. 캐시·기기차이·테스트환경 탓하지 말 것.**
computed style이 내가 원하는 값으로 나와도 실제 화면이 다르면, **그 computed 값이 진짜 이유의 전부가
아닐 가능성부터 의심**해야 한다 — 특히 CSS 특이도(specificity). 파일 순서로 이겼다고 생각한 규칙이,
더 특이도 높은 다른 선택자(`.class:nth-child(n)` 등, 특이도 0,2,0)에 실제로는 지고 있을 수 있다.
`grid-template-columns`처럼 내가 리셋한 속성은 computed로 확인됐어도, `grid-column`/`grid-row`처럼
**다른 속성**을 더 높은 특이도의 선택자가 여전히 강제하고 있으면 배치 자체는 안 바뀐다 — 속성 하나만
확인하고 "코드는 맞다"고 결론 내지 말고, 실제로 영향받는 모든 속성을 개별적으로 재정의했는지 점검할 것.

- 사례: 폴드8 가로힌지 스코프에서 `.training-card{grid-column:auto}`(특이도 0,1,0)로 리셋했는데,
  더 앞선 스코프의 `.training-card:nth-child(n){grid-column:1...}`(특이도 0,2,0)가 여전히 이겨서
  4열 그리드인데도 카드가 좌3/우3 순서로 배치되는 버그가 났음. `grid-template-columns`는 computed로
  4열 확인됐지만 `grid-column`은 확인 안 하고 "코드는 맞다"고 여러 번 캐시·기기 탓을 했던 사례.

## 0-1. 모바일 가로화면의 위상 — "잘 쓰이게" 디자인하는 게 아니라 "안 깨지게" 막는 것 (핵심 원칙)

**모바일 가로모드는 폴드/태블릿 가로모드와 근본적으로 다른 대상이다. 혼동 금지.**

- 모바일은 세로 사용을 권장하는 폼팩터다. 가로 전환 시 그 화면에서 쾌적하게 쓰도록 별도로
  설계하지 않는다 (폴드/태블릿처럼 그 가로 비율 전용 레이아웃을 새로 짜지 않음).
- 그럼에도 가로모드를 완전히 방치해 UI가 깨지면(겹침, 스크롤 불가, 잘림) 사용자는 "가로로는
  안 쓴다"가 아니라 "이 앱 완성도가 낮다"고 느낀다. 또한 사용자는 화면 분할(멀티윈도우)로
  본의 아니게 가로 비율 좁은 화면을 강제로 겪을 수 있다.
- 그래서 모바일 가로모드 대응의 목적은 딱 하나: **세로 레이아웃을 그대로 유지한 채 스크롤을
  허용해서 기능이 막히지 않게만 한다.** 그 화면에 맞춰 열/카드 크기를 재배치하는 게 아니라,
  세로 모드 디자인 그대로 두고 넘치는 부분만 스크롤로 흡수하는 안전장치다.
- 반면 폴드·태블릿의 가로(와이드) 화면은 화면 자체가 넓어서 그 비율에 맞는 전용 레이아웃을
  적극적으로 설계한 것 — 모바일 가로모드와는 목적 자체가 다르다. 폴드/태블릿 작업 패턴
  (다열 그리드 재설계 등)을 모바일 가로모드에 그대로 적용하려 하지 말 것.

## 1. Breakpoint 확정값

| 구분 | 조건 | 대상 |
|---|---|---|
| Mobile | `max-width: 559px` (기본, 조건 없음) | 스마트폰 전종, Z Fold 접힘, Z Flip 펼침 |
| Tablet | `min-width: 560px` and `min-height: 600px` | 태블릿 전종, Z Fold 펼침, 데스크탑 창 반분할 |
| Fold 근접정사각형 (Tablet 하위 예외) | `min-width:580px, max-width:760px, min-height:700px, min-aspect-ratio:3/4, max-aspect-ratio:1/1` | Z Fold 펼침 전종 |
| Desktop/Laptop | `min-width: 1440px` (Tablet 조건 위에 얹힘) | PC·랩탑 브라우저 |

- `min-width:560px`: 갤럭시 폴드3 펼침폭 590px가 걸리도록 낮춘 값(600이면 밀려남). 폴드 접힘폭(~360~412)·일반 폰 세로폭(~480 이하)과 안 겹쳐서 안전.
- `min-height:600px`은 태블릿 조건에 필수 — 없으면 폰 가로모드(812×375처럼 폭만 넓고 높이 낮은 기기)가 같이 걸림.
- `min-width:1440px`: 랩탑(1366/1440/1600) 대부분 커버. 태블릿 실기기 9종 중 가로폭이 이 경계에 닿는 건 Tab S10 FE+(1440px) 하나뿐 — 데스크탑으로 분류하기로 확정(§4 참고). iPad Pro13 M4 가로(1376px)는 경계 아래라 태블릿 유지.
- `hover:none`+`pointer:coarse` 터치 판별은 테스트 툴이 에뮬레이션 안 해서 검증 불가 → 제거함. 비슷한 창 크기의 노트북/데스크탑 브라우저도 태블릿/데스크탑 스타일을 탈 수 있음(허용).

## 2. 홈 탭 CSS 구현 (`style.css` 12133줄~)

### 태블릿 공통 (560px~, 세로/가로 공통 베이스)
- `.app-shell` `max-width:1600px` 중앙정렬
- `#view-home`: `--view-home-gap:16px`, `justify-content:space-between`
- `.home-ad-banner`: `aspect-ratio:unset; height:14vh` (폭 기준 aspect-ratio를 두면 태블릿처럼 폭이 넓어질수록 세로도 커져 넘치는 문제가 있어 `vh` 고정으로 전환)
- `.home-blocks`: 2×2 그리드, `height:44vh`
- `.hdb-row`: `min-height:170px`
- `--view-home-gap` 커스텀 변수 주의: `.home-ad-banner`에 `margin-block: calc(20px - var(--view-home-gap))`가 걸려있어서 gap을 키우면 이 계산식이 자동 상쇄시킴 → 오버라이드할 땐 `.home-ad-banner { margin-block: 0 }`도 같이 꺼야 함 (자세한 삽질 과정은 `docs/debugging_log.md` 2026-08-11 항목)

### 세로(portrait, `max-aspect-ratio:1/1`)
- `#view-home`: `max-width:70%`, `--view-home-gap:36px`, `justify-content:center`
- `.home-blocks`: `height:50vh`

### 가로(landscape, aspect-ratio 조건 없음 = 위 공통값 그대로)
- `#view-home`: `max-width:50%` 중앙정렬

### 낮은 높이 가로 태블릿 예외 (`min-height:600px~max-height:800px` + `min-aspect-ratio:1/1`, 예: 갤럭시탭 1138×712)
- 공통값(44vh/14vh/170px)이 이 높이대에서 가용공간을 넘어 넘침 → 축소
- `.hdb-row:110px`, `.home-ad-banner:12vh`, `.home-blocks:34vh`

### 모바일(~559px) 공통 — 홈블럭 유동 높이
- `.home-blocks`: 고정 `aspect-ratio:5/7` 대신 `flex:1 1 0`으로 전환, `grid-template-rows: repeat(2, minmax(0,1fr))` — 저높이 프리셋에서 하단이 잘리는 문제 해결. **`minmax(0,1fr)` 필수** — 그냥 `1fr`이면 CSS Grid 트랙 자체가 콘텐츠 최소높이 밑으로 안 줄어들어(flex의 `min-height:0`과 별개 문제) 빠듯한 화면(Flip)에서 넘침
- `.home-block`: `aspect-ratio:unset; width/height:100%`
- 모바일 브라우저(주소창 등으로 세로공간 줄어든 저높이, `max-height:750px`) — 앱 풀스크린과 분리해서 `.hdb-banner` padding 축소, `.home-ad-banner` aspect-ratio 4.2/1로 얇게

### Z Flip 세로(`min-width:355px, max-width:365px, min-height:820px, max-height:900px`)
- 힌지가 물리 뷰포트 정확히 50%(모든 기종 공통)라서, **px/vh 값을 직접 계산해 넣는 방식은 기기별 높이(840/880) 차이로 매번 깨짐** — flex-grow 비율 기반으로 전환
- `home.html`에 `.home-top-stack` wrapper 추가(`.hdb-banner`+`.home-ad-banner` 묶음). 기본값은 `display:contents`(레이아웃 투명, 다른 화면 영향 없음) — Flip 스코프에서만 `display:flex; flex-direction:column`로 활성화, **`width:100%` 필수**(안 주면 `#view-home`의 `align-items:center`가 내재폭으로 퍼져서 화면 밖으로 넘침)
- `#view-home`은 flex column 그대로 두고 `.home-top-stack{flex:54 1 0}` / `.home-blocks{flex:46 1 0}`로 남는 공간만 비율 분배 — 컨테이너 실제 렌더 높이가 얼마든 합이 항상 100%라 구조적으로 안 넘침(자기-적합). 54:46은 힌지가 물리 화면 정중앙이란 사실에서 낸 근사치(`#view-home` 자체는 바텀탭만큼 짧아서 정확히 50:50은 아님)
- **margin은 `height:100%`/`flex`와 같이 쓰면 셀보다 커져서 넘침** — 여백은 반드시 `padding`으로(border-box라 height 안에 포함됨), 기본 `.home-blocks{margin-bottom:20px}`도 Flip 스코프에서 `margin:0`으로 취소
- 확정값: `.hdb-banner{padding:26px 16px}`, `.hdb-row{min-height:120px}`, `.home-ad-banner{aspect-ratio:3.2/1}`, `.home-blocks{padding:10px 0 24px}`

### Z Fold 펼침 전종 (근접정사각형 예외, `min-width:580px, max-width:760px, min-height:700px, min-aspect-ratio:3/4, max-aspect-ratio:1/1`)
- `#view-home`: `max-width:82%`, `--view-home-gap:24px`
- `.home-ad-banner:12vh`, `.home-blocks:46vh`, `.hdb-row:12vh`(px에서 vh로 통일, Fold7 832px 기준 환산), `.home-blocks{column-gap:64px}`(힌지 세로선 기준 좌우 카드 벌림, row-gap은 기본 12px 유지)
- 실기기 7종 종횡비: 폴드2 .801 / 폴드3 .801 / 폴드5·4 .832 / 폴드6 .859 / 폴드7 .901 / 폴드8U .901 / **폴드8(신형) .755**(iPad에 근접) — 폴드8만 비율이 달라서 `min-aspect-ratio` 기준을 3/4(.75)까지 낮추고 `max-width:760px`으로 iPad 표준/에어를 폭에서 차단, iPad mini(.656)는 비율 미달로 자동 제외

### 데스크탑/랩탑 사이드바 (1440px~)
- `.app-shell`을 grid로 전환: `grid-template-areas: "nav topbar" / "nav main"` — 좌측 `nav`가 두 행 다 차지, `topbar`는 우측 컬럼 위쪽에만
- `.bottom-nav`가 하단탭 대신 좌측 240px 세로 사이드바로 재사용(HTML 그대로, CSS로 flex row→column)
- 사이드바 구성(위→아래): 타이틀(`.sidebar-brand`) → 유저요약(`.sidebar-user`) → 홈/노트/프로필 → 튜토리얼 → *(빈공간)* → 설정 → 로그아웃(`position:absolute; bottom` — `margin-top:auto`는 컨테이너 높이 계산 이슈로 안 먹어서 폐기)
- 튜토리얼/설정 버튼은 **실제 DOM을 JS로 이동**(복제 아님) — `home.js`의 `matchMedia('(min-width:1440px)')` change 리스너가 데스크탑이면 `.bottom-nav`로, 아니면 `.top-bar`로 옮김. 탭별 hidden 토글은 ID 기반이라 위치 이동과 무관하게 작동, 사이드바 안에서만 hidden 무시하고 항상 노출되도록 오버라이드
- 로그아웃은 사이드바 전용 새 버튼(`#sidebar-logout-btn`), 유저요약은 `#tbl-num`/`#profile-name`/`#profile-plan-name`을 `MutationObserver`로 미러링 + `loadProfileFromDB()` 앱 시작 시 1회 선행 호출
- **주의**: 태블릿 범위(560~1440 전체)에 nav rail 그대로 적용하면 깨짐 — 반드시 데스크탑(1440px~)에만 좁혀서 적용할 것

- Fold8 Ultra: Cover 360×840(9:21), Main(펼침) **835×752**(10:9)
- 기존 Fold(2~7)는 펼침 기본이 세로로 긴데, Fold8 시리즈는 책처럼 좌우로 펼쳐져 기본이 가로로 넓음 — 힌지는 이 기본 방향에서 세로, 90도 돌리면(704×933/752×835) 가로로 반전. 홈탭 레이아웃(2×2 그리드 비율 등)은 아직 미착수, 힌지 오버레이만 반영됨(§3)

### Z Fold 분할화면(안드로이드 멀티윈도우)

## 6. svh/dvh 정책

- 풀스크린 컨테이너(`body`, `.app-shell`, `#page-cover`)는 `100svh` 채택(구형 브라우저용 `vh` 폴백 유지) — 외부 브라우저에서 주소창 접혔다 펼쳐질 때 `dvh`는 매번 재계산되며 흔들리는데 `svh`는 최소 보장값 고정이라 안 흔들림. 대신 주소창이 완전히 숨겨진 상태에선 화면 하단에 배경색만큼 여백이 살짝 남을 수 있음(트레이드오프로 감수).
- 에디터 페이지 모바일 드로어 사이드바(`.sidebar`, 3475·3830줄 부근)는 아직 `100dvh` — 홈탭 스코프 밖이라 안 건드림.
- `#view-home`은 `overflow-y:auto` + flex 기반이라 저높이(635px)에서도 스크롤로 흡수, 폭 360~412px 구간도 %/flex/clamp라 별도 분기 불필요.

## 6-1. 디버깅 원칙 — 바깥 여백보다 안쪽 콘텐츠를 먼저 의심

여백/간격이 지정한 값대로 안 보일 때, **바깥 컨테이너의 단위(vh·%·gap·margin)를 손대기 전에 내부 콘텐츠가 그 박스를 채우고 있는지부터 확인할 것.**

- 컨테이너에 `2vh`를 줬는데 화면에선 훨씬 넓어 보이는 상황이 반복됐는데, 실측해보니 `margin-bottom`은 정확히 2vh(15.48px/16px/20.64px, 전 기기 정상)였음. 진짜 원인은 **카드 내부가 세로 적층(flex column)이라 낮고 넓은 카드에서 아이콘과 텍스트 사이가 벌어져 빈 공간이 생긴 것** — 바깥 여백이 아니라 안쪽 배치 문제였음.
- 반대 방향 사례도 같은 뿌리: 콘텐츠 필요높이가 카드보다 크면 `overflow`가 하단 패딩을 잘라먹어서 "패딩을 줬는데 안 보인다"가 됨(Fold8 홈블럭, 카드 123px vs 콘텐츠 146px).
- **점검 순서**: ① 콘솔로 실측(`getBoundingClientRect`, `scrollHeight` vs `clientHeight`) → ② 값이 맞으면 바깥 단위는 범인이 아님 → ③ 내부 배치(적층 방향·`justify-content`·grid 행 배분)를 본다.
- 낮고 넓은 카드(가로모드·폴더블 와이드)는 세로 적층이 구조적으로 안 맞음 → 아이콘 좌 / 텍스트 우 2열 그리드가 정답. 세로로 긴 카드(모바일·태블릿 세로)는 반대로 세로 적층 유지.

## 8. 홈 탭(홈/노트/프로필/바텀시트) 반응형 완료 — 실수 사례와 원인 찾은 과정

전 탭 세로→가로→태블릿→데스크탑 순으로 개별 뷰포트 튜닝 완료. 디테일 이슈는 다음 버전에서. 아래는 작업 중 실제로 틀렸던 부분과, 추측 대신 무엇을 확인해서 원인을 잡았는지 기록.

### 8-1. www/ 미동기화를 "CSS 안 먹는다"로 오인
- 증상: 규칙을 고쳐도 화면에 반영 안 됨 → 몇 차례 "왜 안 바뀌지" 헤맴.
- 원인 확인: `getComputedStyle(el).color` 실측 → 옛 값 그대로. `document.styleSheets`에서 해당 selectorText 검색 → `undefined`(그 규칙 자체가 로드된 CSS에 없음). `www/style.css`에 같은 selector grep → 없음. 즉 브라우저가 루트가 아니라 `www/`를 보고 있었음.
- 교훈: 이후 매 CSS/HTML 수정 직후 `www/` 동기화를 습관화(`cp style.css www/style.css` 등). "그럴리 없다"는 반응이 나와도 실측(`document.styleSheets` 조회)으로 먼저 확인하고 캐시나 www 여부를 가리는 게 맞았음.

### 8-2. 모바일 가로모드 판별 시 `min-height` 가드 누락
- 증상: `#main-content`가 812px 뷰포트에서 400px로 캡됨(하단탭 흰 배경이 풀폭이 아님).
- 원인: 구버전 "데스크탑에서도 앱을 폰 폭으로 캡"하는 레거시 규칙이 `min-width:480px` 단독 조건이라, 폭만 넓고 높이 낮은 모바일 가로모드도 같이 걸림.
- 확립된 원칙(§1)과 어긋난 실수: 태블릿 판별은 항상 `min-width AND min-height` 조합이어야 하는데, 오래된 규칙 하나가 이 패턴을 안 따르고 있었음. `min-height:600px` 추가해서 해결.
- 교훈: 새 반응형 규칙을 짤 때뿐 아니라, **기존 레거시 규칙도 같은 판별 패턴을 따르는지 점검**해야 함.

### 8-3. `position:absolute` 요소와 일반 flex 아이템의 `max-width + margin:auto` 차이
- 증상: `#view-profile`에 `max-width:90%; margin-inline:auto`를 걸었는데 실측 폭이 750px 중 292px(39%)만 나옴.
- 확인 과정: `.app-shell` 실폭 750px(정상) → `getComputedStyle` 확인 결과 `max-width` 자체는 90%로 정확히 매칭 중 → 그런데도 렌더 폭은 훨씬 작음.
- 원인: `#view-profile`은 `position:absolute`가 아니라 일반 flex 컬럼 아이템. `margin:auto`(cross-axis auto margin)가 flex의 기본 `stretch` 동작을 꺼버려서, `max-width`는 상한만 정할 뿐 그 크기까지 채워주지 않고 콘텐츠 크기로 shrink-to-fit됨.
- 반면 `#view-home`/`#view-projects-list`는 `position:absolute; inset:0`이라 `left:0;right:0` + `width`+`margin:auto` 조합이 CSS 과잉제약(over-constrained) 규칙으로 자동 중앙정렬됨 — 같은 트릭이지만 포지셔닝 방식에 따라 결과가 다름.
- 해결: `max-width` 대신 `width`를 명시(고정폭 강제, stretch 여부와 무관하게 항상 그 값).
- 교훈: 같은 "폭 제한 + 중앙정렬" 패턴도 요소가 `position:absolute`인지 일반 in-flow flex 아이템인지에 따라 `max-width`와 `width`의 동작이 달라짐 — 매번 실제 렌더 폭을 재서 확인.

### 8-4. `flex:1 1 0; min-height:0`을 고정 높이 없는 부모에 쓰면 콘텐츠가 겹침
- 증상: `.profile-container--stats`와 `.profile-container--invite`가 실제로 겹침(사용자가 육안으로 바로 확인).
- 원인: 부모를 `height`(고정)에서 `min-height`(최소값만)로 바꾼 뒤에도, 자식(`.profile-stats` 등)에 `flex:1 1 0; min-height:0`이 남아있었음. 부모 높이가 확정값이 아니면 `flex-basis:0` 자식은 분배할 확정 공간이 없어 박스 자체가 거의 0으로 접히는데, 실제 콘텐츠(카드 4개)는 그대로 렌더링돼 접힌 박스 밖으로 튀어나와 다음 섹션과 겹침.
- 해결: `flex:1 1 0; min-height:0` 강제를 제거하고 자연스러운 콘텐츠 크기로 되돌림.
- 교훈: `height`→`min-height`처럼 부모의 높이 확정 방식을 바꿀 때는, 그 확정 높이를 전제로 짠 자식의 flex-grow/min-height:0 규칙도 같이 재검토해야 함. 짝을 이루는 규칙이었다는 걸 놓치면 한쪽만 고치고 다른 쪽 때문에 깨짐.

### 8-5. `:nth-of-type`은 클래스가 아니라 태그 전체를 셈
- 증상: 통계/초대코드 카드에 순서대로 높이를 주려고 `.profile-container:nth-of-type(1/2/3)`을 썼는데, 카드 하나(코드입력)가 스타일을 아예 못 받음.
- 원인: `:nth-of-type`은 "같은 태그(div)를 가진 형제 중 n번째"를 셈 — 클래스 필터링이 없음. 그 앞에 클래스가 다른 wrapper `div`(`.profile-top-stack`)가 하나 끼어 있어서 인덱스가 통째로 하나씩 밀림.
- 해결: 순번 기반 선택자 대신 `.profile-container--stats`/`--invite`/`--code` 같은 전용 클래스로 직접 타겟팅.
- 교훈: 형제 요소 중 일부만 특정 클래스를 가질 때 `:nth-of-type`/`:nth-child`는 예측과 다르게 동작하기 쉬움 — 순서가 아니라 전용 클래스로 명시하는 게 안전.

### 핵심 구조 결정 — 오버레이를 걷어내고 캔버스 좌표계를 DOM으로 복제
가장 큰 난제는 **좌표계가 두 개로 갈라져 있던 것**이었다.
- 캔버스 내부(dot·프렛번호·개방현)는 `BASE_*` 상수(440×352, 5:4) 비율로만 그려져 원래 안전했다.
- 문제는 주변 버튼들이 **위치는 카드 기준(px), 크기는 캔버스 기준(`displayW` 비례)** 으로 잡혀 있던 것. 두 기준이 서로 다른 속도로 변해 뷰포트마다 관계가 틀어졌다.
- 증상 예: `.canvas-unit{padding-top:30px}` 매직넘버(샵플랫 토글 자리 확보용), 카드 패딩은 `%`인데 토글은 `14px` 고정이라 폰/태블릿에서 여백 역전, `transform:scale()`과 `top/left`가 따로 노는 문제.

**해결**: `.canvas-inner`를 grid로 만들고 캔버스 비트맵의 구성비를 그대로 복제.
```
컬럼: 105/240/95 → 23.864% / 54.545% / 21.591%
행  :  80/192/80 → 22.727% / 54.545% / 22.727%
```
캔버스는 `grid-area: 1/1/-1/-1`로 전체를 덮는 배경 레이어, 버튼 6개(샵플랫·초기화·저장·재생·프렛화살표·바레)는 각자 셀의 정식 구성원이 됐다. `aspect-ratio: 440/352` 필수 — 없으면 % 행이 auto로 무너진다.

**효과**: 개별 `top/right/px` 계산이 전부 사라지고 grid-template 한 곳에서 결정. `resizeCanvas()`의 JS 배치 코드 ~50줄 삭제, `requestAnimationFrame` 재측정 2곳 제거(뷰가 hidden일 때 rect=0이라 엉뚱한 값이 박히던 버그도 같이 해결).

⚠️ **`BASE_*` 상수는 절대 변경 금지** — `voicing-canvas.js`를 통해 팔레트·코드사전·노트슬롯·저장이미지까지 공용이라 바꾸면 앱 전체 다이어그램 모양이 바뀐다. CSS의 %는 이 상수를 '복제'만 한 것.

### 정방형·와이드 뷰포트 전략 — 2번안(좌우 버리기) 확정
Fold 펼침처럼 정방형에 가까워지면 카드가 뷰포트 폭만큼 늘어나 캔버스(폭 기준 확대)까지 비정상적으로 커진다. 두 선택지 중:
1. 새 배치로 최적화(캔버스+휠피커 좌우 분할 등)
2. 세로로 긴 이너에디터 유지하고 좌우 공간 버리기

→ **2번 확정**(사용자). 이유: `#view-project`(노트 에디터)에 검증된 폭 캡 패턴이 이미 있어 재사용 가능, 새 버그 표면적 최소, 방금 완성한 캔버스 grid를 안 건드림.

- 사용자 육안 확인: **320~340px 사이가 제일 보기 좋음** (400px·360px은 커 보였음).
- 1440px 기준 400px = 27.78vw → 데스크탑은 `vw` 기준으로 전환.

### 실수 사례와 원인 찾은 과정

#### 10-1. 캐스케이드 — 파일 등장 순서
스코프 블록을 base 규칙보다 **앞**에 두면 통째로 무효화된다. `.chord-preview`/`.chord-display`/`.chord-suggest-item`의 base가 1900번대에 있는데 태블릿 스코프를 1497줄에 뒀다가 `align-items`·폰트·패딩이 전부 안 먹었다.
- **찾은 방법**: "안 되는데?" 소리를 듣고 `grep -n`으로 같은 셀렉터 전부 나열 → base가 스코프보다 뒤에 있는 걸 눈으로 확인.
- **교훈**: 새 미디어쿼리 블록은 그 셀렉터의 base 규칙 **뒤**에 배치. 관련 블록끼리 모아두면 순서가 자연히 지켜진다.

#### 10-2. 캐스케이드 — 명세 우선순위
`@media(max-width:1400px)` 안에 `.builder-col .sel-btn`(클래스 2개)가 있어서, 순서를 맞춰도 plain `.sel-btn` 오버라이드가 **항상** 졌다.
- **찾은 방법**: 순서를 고쳤는데도 안 먹혀서 `grep`으로 `.sel-btn` 전체 나열 → 결합 셀렉터 발견.
- **해결**: 그 블록 **뒤**에 같은 명세(`.builder-col .sel-btn`)로 다시 덮음. 현재 태블릿세로/Fold세로/Fold가로 3개가 거기 모여 있다.
- **교훈**: 순서를 고쳐도 안 먹으면 **명세**를 의심. `grep`으로 결합 셀렉터가 있는지 먼저 본다.

#### 10-3. 스코프 상속 누수 — Fold8이 태블릿 값을 물려받음
Fold8 회전(704×933)이 태블릿 세로 조건(`min-width:560, min-height:600, aspect≤1`)에 같이 걸려서, 카드는 340px로 좁아졌는데 폰트·피커높이만 태블릿 확대값이 남아 휠피커가 비정상적으로 길어졌다.
- **찾은 방법**: 사용자가 "Z폴드8만 유난히 길다"고 지목 → 조건식을 겹쳐보고 두 스코프가 교집합인 걸 확인.
- **해결**: Fold 스코프에서 `--picker-item-h`·폰트·패딩을 모바일 기준으로 **명시적 리셋**.
- **교훈**: 넓은 조건의 스코프를 만들면 의도치 않은 기기가 딸려 들어온다. 좁은 스코프에서 되돌릴 값 목록을 같이 만들 것.

#### 10-4. 클래스 공유로 인한 누수 — 사이드바 경험치바
`@media(min-width:1440px)`의 `.profile-xp{width:calc(50% - 16px)}`(프로필 탭 폴드 힌지 정렬용)이 **같은 클래스를 쓰는 사이드바 XP바**에도 새어들어가 폭이 91.5px로 줄어 사라진 것처럼 보였다.
- **찾은 방법**: 실측(`getBoundingClientRect` + `getComputedStyle`)으로 `width: 91.5px` 확인 → 부모 콘텐츠폭 215px의 `50% - 16px`와 정확히 일치하는 걸 계산으로 대조.
- **해결**: `.sidebar-user-xp.profile-xp`(클래스 2개, 명세 높음)에 `width:100%`.
- **교훈**: `.profile-*` 계열을 건드릴 때 사이드바 미러 요소(`.sidebar-user-*`)도 같이 확인.

#### 10-5. `justify-content:center`로 세로 중앙정렬 금지
콘텐츠가 컨테이너보다 클 때 `justify-content:center`는 **위쪽 넘친 부분이 스크롤로 접근 불가능**해진다(아래로만 스크롤됨).
- **찾은 방법**: 사용자가 "하단은 되는데 상단 끝까지 스크롤이 아예 안 된다"고 보고 → 알려진 flexbox 동작으로 즉시 특정.
- **해결**: 타이틀 `margin-top:auto` + 카드 `margin-bottom:auto` 조합. auto margin은 넘치면 0으로 collapse돼 이 문제가 없다.
- **부작용 처리**: `margin:20px` shorthand가 `margin-top`도 잡아 타이틀 `margin-bottom`과 합산(12+20=32px)돼서 `margin-top:0`으로 분리. 하단 20px 여백도 auto에 먹혀 사라져서 `#view-editor{padding:0 0 20px}`로 부모에 옮김.

#### 10-6. 타이틀 정렬 — base만 깨뜨려놓고 스코프만 확인
"타이틀 좌측 6px" 요청에 base의 `padding: 0 20px`을 `0 0 0 6px`로 바꿨는데, **그 20px이 카드의 `margin:20px`와 짝을 이루던 정렬 기준**이었다. 모바일에서만 타이틀이 카드보다 14px 왼쪽으로 튀어나갔고, 스코프들은 `margin-inline:auto`+동일 width라 안 깨져서 데스크탑만 보면 멀쩡했다.
- **찾은 방법**: 사용자가 "완전히 꼬였다, 구조를 전면 재분석하라"고 지시 → HTML 구조부터 모든 스코프의 카드/타이틀 가로 박스를 표로 나열 → base 한 줄만 ❌인 걸 발견.
- **해결**: 불변식으로 정리 — **타이틀 가로 박스 = 카드 가로 박스 + `padding-left:6px`**. base는 둘 다 `margin-inline:20px`, 스코프는 둘 다 `width:N`+`margin-inline:auto`.
- **교훈**: 한 스코프만 보고 "됐다" 하지 말 것. 형제 요소 정렬은 **양쪽 가로 박스를 표로 나열**해야 빠진 곳이 보인다.

#### 10-7. 높이 캡 — `vh`를 컨테이너 높이로 착각
카드는 폭으로만 크기가 정해지므로 세로가 짧은 뷰포트에선 `width: min(폭캡, Nvh)`로 높이 제약을 걸어야 한다. 처음엔 종횡비를 1.68로 **추정**해 47vh를 넣었는데 67px 넘쳤다.
- **찾은 방법**: 추측으로 값을 내리는 대신 실측 → 종횡비가 실제로 **1.815**였고, 더 중요하게 **`vh`는 `innerHeight`(704) 기준인데 `#view-editor` 실제 높이는 590px**(탑바+하단탭이 114px)이라 근본적으로 과대평가되고 있었다.
- **공식 확립**:
  ```
  가용   = #view-editor.clientHeight − 타이틀높이 − 타이틀 margin-bottom − padding-bottom
  필요폭 = 가용 / 1.815
  N      = 필요폭 / innerHeight × 100
  ```
- **교훈**: `vh`≠컨테이너 높이. 비율은 추정하지 말고 `getBoundingClientRect`로 재고, `scrollHeight - clientHeight`로 넘침량을 직접 확인한다. (§6-1 "측정은 추측보다 우선"의 재확인)

#### 10-8. `resizeCanvas()`가 stale 값으로 남던 문제
미디어쿼리로 `.editor-card` 폭이 바뀌어도 `window.resize`가 안 일어나면 `canvas.style.width`가 옛 값 그대로 남아, 캔버스가 부모(404px)보다 큰 623px로 튀어나왔다.
- **찾은 방법**: 실측으로 `.canvas-unit`은 정상인데 `#c`만 623px인 걸 확인 → 호출 지점을 grep해 `resize` 이벤트와 뷰 진입 rAF 두 곳뿐인 걸 발견.
- **해결**: `.canvas-unit`에 `ResizeObserver`. 원인(리사이즈·뷰전환·미디어쿼리)과 무관하게 항상 재계산. 캔버스는 부모 폭을 따라가기만 하므로 순환 없음.

#### 10-9. JS 상수와 CSS 변수의 이중 관리
`--picker-item-h: 30px`와 `home.js`의 `PICKER_ITEM_H = 30`이 따로 있어서, 스코프별로 CSS만 바꾸면 스크롤 스냅 계산이 어긋났다.
- **해결**: JS가 `getComputedStyle`로 CSS 변수를 실시간으로 읽게 전환. `resize` 시 재동기화하고, 값이 바뀌면 이미 열린 휠들의 `scrollTop`도 idx를 유지한 채 새 pitch로 재정렬.
- **교훈**: 같은 값을 두 곳에 적으면 반드시 어긋난다. **단일 소스(CSS 변수) + 읽기 전용 참조**로 통일.

### 데스크탑 전용 — 뒤로가기 버튼 DOM 이동
데스크탑 grid는 `"topbar topbar" / "nav main"`이라 `.top-bar`가 사이드바+메인 전체를 가로지른다. `#back-btn`이 그 안에 있으면 좌측 끝이 사이드바 위에 떠서 메인 콘텐츠 좌상단과 안 맞는다. CSS 포지션으로는 못 고치고 **DOM 위치 자체를 옮겨야 한다** — `matchMedia`로 `.top-bar` ↔ `#main-content` 간 이동(튜토리얼/설정 버튼과 동일 패턴, §2 참고).

### 절대 규칙 및 기본 구조
`#view-library` 직계 4형제: `.lib-title` → `.lib-search-bar` → `.lib-viewer`(캔버스+사이드버튼+운지내비) → `.lib-bottom-area`(액션바+근음리스트+카드그리드). 와이드 뷰포트(태블릿 가로 이상)에서는 근음 레일을 좌측 컬럼으로 분리하고, 다이어그램+액션바를 하나로 묶어 우측 컬럼에 배치하는 3컬럼 grid로 재구성했다.

### 가장 어려웠던 부분 — 두 번의 구조적 실패와 최종 해법

**1차 시도: `display:contents` 래퍼로 실패**
와이드 레이아웃에서 "타이틀+검색+다이어그램을 합쳐서 50vh로" 만들려고 `.lib-top-stack`(래퍼 div, `display:contents`)으로 형제 요소들을 묶었다. `display:contents`는 요소 자체를 레이아웃에서 지우고 자식만 부모의 flex/grid 아이템으로 승격시키는 속성인데, 실제로는 자식들이 flex 아이템으로 전혀 승격되지 않고 `.lib-bottom-area`만 정상 flex 아이템으로 잡히는 기현상이 발생 — 타이틀·검색·캔버스가 전부 겹쳐 그려지고 모바일 하한이 완전히 깨졌다.
- **찾은 방법**: 사용자가 스크린샷으로 "#/b 토글이 타이틀 바로 아래 있고 하단 영역이 사라졌다"고 보고 → DOM 트리를 `console.log`로 재귀 덤프해 `#view-library`의 실제 자식이 `.lib-top-stack` 하나뿐이고 나머지는 그 안에 중첩된 걸 확인.
- **해결**: `display:contents` 래퍼를 완전히 철거하고 4형제 구조로 복귀. 와이드 레이아웃에서 "묶기"가 필요한 곳은 진짜 `display:grid`/`flex` 컨테이너(`.lib-bottom-area`를 자체 2행 그리드로 만드는 식)로 대체했다.
- **교훈**: `display:contents`는 스타일링 목적의 그룹핑에 못 쓴다. 그룹이 필요하면 실제 박스(grid/flex)를 만들 것.

**2차 시도: 컬럼 간 행 트랙 공유로 인한 상호 오염**
와이드 3컬럼 grid에서 초기에는 outer grid의 모든 행(검색/다이어그램/액션바)을 `.lib-title`과 `.lib-bottom-area`(카드)도 같이 공유하게 짰다. 그 결과 "타이틀 높이가 12key의 한 칸(root-item) 높이로 고정된 것처럼 보인다"는 현상이 나타났다 — 실제로는 검색바의 `margin-top`이 outer grid의 1번 행 트랙 높이를 정하고 있었고, 타이틀은 그 트랙 안에서 남는 공간만큼 여백처럼 보인 것.
- **찾은 방법**: 처음엔 devtools grid 오버레이를 좌표로 짚어보려 했으나 사용자가 "좌표측정으로 안 나올 것 같다, 특성으로 유추하자"고 지적 — 클릭 시 스케일 축소 애니메이션이 있고 홈으로 이동하는 요소라는 특징으로 `#back-btn`임을 특정. 이 사례는 다이어그램이 아니라 별개(§ 아래)지만, "행 공유로 서로 다른 컬럼이 크기에 영향을 준다"는 패턴은 동일하게 반복됐다.
- **해결**: 가운데 컬럼(레일 옆, 타이틀+카드)을 `.lib-bottom-area` 자체의 **독립된 2행 그리드**(`grid-template-rows: auto 1fr`)로 만들어 outer grid의 행 트랙과 완전히 분리. `home.js`가 `.lib-title`을 `.lib-bottom-area` 안으로 이동시켜 이 내부 그리드에 소속시킨다. 이후 오른쪽 컬럼(검색/다이어그램/액션바)이 outer 행을 몇 개 쓰든 가운데 컬럼과 서로 영향이 없어졌다.
- **교훈**: "3컬럼인데 컬럼마다 필요한 행 개수가 다르면" 공유 grid로 억지로 맞추지 말고, 서로 다른 개수가 필요한 컬럼을 자체 내부 grid로 독립시킨다.

### 반복적으로 재발한 문제 — 캐스케이드 파일 순서

이번 작업에서 최소 3번 같은 함정에 걸렸다(§10-1과 동일 유형, 코드 에디터에서 이미 겪은 교훈인데도 또 반복됨):
1. `.lib-voicing-grid`(운지폼 모달 그리드)를 와이드 스코프에서 4열로 바꿨는데 base 규칙(`repeat(3,1fr)`)이 파일 뒤쪽에 있어서 안 먹음.
2. 코드 사전 카드 그리드 열 개수를 5→4로 재조정하면서 예전에 만든 "구 데스크탑 5열/FHD 6열" 블록이 죽은 채로 남아있었음(뒤에 새 4열 블록이 있어 실제로는 안 보였지만 파일이 지저분했음) — 이번에 발견하고 정리.
3. `.lib-bottom-area`에 새 `#lib-canvas` 폭 값을 넣었는데 바로 아래 예전 값이 중복 선언으로 남아있어 무효화됨.
- **교훈**: "고쳤는데 안 먹는다"는 보고를 받으면 항상 같은 셀렉터를 `grep`으로 전부 나열해서 파일 순서부터 확인. 이 프로젝트에서 CSS를 고칠 때 가장 먼저 의심해야 할 원인 1순위.

### 미디어쿼리 스코프 중첩(같은 해상도가 여러 스코프에 동시 매치)

폴더블 기기는 폭/높이/종횡비 숫자가 여러 스코프 조건에 동시 히트하는 경우가 잦다:
- Z Fold8 표준형(933×704)이 "Fold 가로힌지"(700~760h, aspect 1/1~4/3) 스코프에도 들어감(933/704=1.325 < 4/3).
- Z Fold8 회전형(704×933)이 "Fold 세로힌지"(580~760w, aspect 3/4~1/1) 스코프에도 들어감(704/933=0.755, 580~760 폭 범위 안).
- **찾은 방법**: 실측으로 "그리드 하단 흰 여백 + 카드 우측 살짝 잘림"을 확인한 뒤 "혹시 폴드메인과 같이 적용됐나?"라는 사용자의 직관적 의심을 좌표/폭 계산으로 검증 → 정확히 겹치는 걸 확인.
- **해결**: Fold8 전용 조건(폭 834~950 또는 680~770)이 상대 스코프보다 좁아서 자동으로 걸리므로, Fold8 전용 블록을 파일에서 **더 뒤에** 두어 같은 프로퍼티는 이기게 하고, Fold8만의 값(그리드 비율·캔버스 크기·카드 열 수)을 새로 계산해서 분리했다.
- **교훈**: 폴더블 스코프를 새로 추가할 때는 기존 스코프 조건과 폭/높이/종횡비 숫자가 겹치는지 항상 먼저 계산해볼 것. "왜 두 기기가 같은 값을 공유하지?"가 아니라 "왜 다른 스코프인데 조건이 겹치지?"를 물어야 한다.

### vh 수동 계산 대신 flex:1로 전환 (뒤늦게 발견한 더 단순한 해법)

Fold 세로힌지·Fold8 회전형처럼 grid가 아니라 일반 flex-column으로 쌓이는 스코프에서, "그리드 영역이 몇 vh가 되어야 화면에 딱 맞는가"를 캔버스 크기·패딩·타이틀/검색바 높이를 전부 실측해 매번 손으로 계산했다(§10-7 Nvh 공식과 같은 방식). 그런데 값을 조금만 바꿔도(그리드 45→60→50→45vh, 캔버스 크기 변경) 매번 다시 계산해야 했고, 계산 실수나 중복 규칙 잔존으로 여러 번 틀렸다.
- **찾은 방법**: 사용자가 "캔버스 크기를 정하면 남는 영역이 그리드 영역 아니야?"라고 직접 지적.
- **해결**: `.lib-bottom-area`를 `height: Nvh` 고정 대신 `flex: 1; min-height: 0`으로 되돌리고, 캔버스만 고정 px로 정하면 나머지 공간을 그리드가 자동으로 채운다. 애초에 `.lib-bottom-area`의 base 규칙이 `flex:1`이었는데 그 위에 vh 고정값을 계속 덮어씌우며 스스로 복잡하게 만들고 있었던 것.
- **교훈**: flex 컨테이너 안에서 "남는 공간을 정확히 채워야 하는 요소"가 있으면, 그 요소의 형제들 크기만 고정하고 그 요소 자체는 `flex:1`로 두는 게 vh 계산보다 항상 더 정확하고 더 단순하다. Nvh 계산은 **grid의 다른 트랙이 이미 고정 비율(vh)로 서로 얽혀있어서 flex로 못 바꾸는 경우**(코드 에디터의 캔버스 카드처럼)에만 최후 수단으로 써야 한다.

### 그 외 실수 사례

- **`border-radius:50%`가 막대바로 바뀌면서 괴상한 곡선으로 변형**: `#back-btn`을 20px 아이콘 버튼에서 전체 폭 56px 탑바로 바꾸면서, base의 `border-radius:50%`(정사각형 아이콘 기준 원형)를 안 지웠다. 가로로 아주 넓고 얇은 사각형에 50% radius를 주면 모서리가 극단적으로 눌려 알약보다 훨씬 과장된 "스타디움" 모양이 되고, 흰 배경 위에 흰 버튼이라 대부분 안 보이고 둥글게 휜 테두리 끝만 곡선처럼 튀어나와 보였다. **찾은 방법**: 좌표 클릭 조사가 안 통해서, 사용자가 직접 "클릭하면 홀드 시 축소, 놓으면 복원, 클릭하면 홈으로 이동"이라는 **동작 특성**으로 후보를 좁혔다. `:active{transform:scale(0.92)}`+`onclick=home이동`은 `#back-btn` 고유의 서명이라 바로 특정됐다. **교훈**: 시각적 버그가 좌표 조사로 안 잡히면, 그 도형의 인터랙션(클릭 시 반응·애니메이션)이 어떤 요소 고유의 서명인지 물어서 후보를 좁힌다.
- **캔버스 업스케일 블러 — 두 겹의 원인**: 뷰어/카드 캔버스 전부 CSS 표시폭은 스코프마다 다른데 비트맵 해상도(`LIB_VIEWER_W`/`LIB_MINI_W`)는 320px/56px로 고정돼 있어 와이드 레이아웃에서 업스케일되어 흐렸다. `_libViewerRatio()`/`_drawLibMiniCanvas()`로 표시폭을 실측해 비트맵을 그때그때 맞추도록 고쳤는데, 보이싱 모달 안 카드만 여전히 흐렸다. 원인은 `.lib-voicing-modal`이 열리기 전 `transform:scale(0)` 상태라 `getBoundingClientRect()`가 0을 반환해 fallback값(56px)으로 계속 그려졌기 때문 — `offsetWidth`(transform 영향 안 받는 레이아웃 크기)로 바꿔 해결.
- **뷰 진입 시 캔버스가 작게 그려졌다가 커지는 튐**: 뷰가 `hidden`에서 풀리는 바로 그 tick에 캔버스를 측정해서 그리면 레이아웃이 아직 확정 전이라 작은 값이 잡힌다. `selectLibEntry`·`renderLibCards` 호출을 `requestAnimationFrame`(데스크탑은 사이드바 관련 리스너가 더 있어 2중 rAF)으로 미뤄서 레이아웃 확정 후 첫 그리기가 나가게 했다. **미해결**: 데스크탑에서 이 수정 이후 재현 여부를 사용자가 확정하지 않고 다음 작업으로 넘어감.
- **인라인 스타일 높이 고정이 CSS를 이김**: 좁은 화면에서 `.lib-bottom`의 실측 높이를 인라인으로 얼려두는 로직이 있었는데, 이 조건을 JS의 `libWideMq()` 문자열 목록으로 판별하다 보니 새 와이드 스코프(Fold8)를 추가할 때마다 목록이 어긋나 얼어붙는 문제가 재발했다. **해결**: 문자열 목록 대신 `getComputedStyle(.lib-bottom-area).display === 'grid'`로 **실제 CSS 상태를 직접 물어보게** 바꿔서, 스코프 목록이 몇 개든 항상 정확하게 판별하도록 구조를 바꿨다.
- **소프트 코딩으로 이중 관리 제거**: `.lib-cards`와 `.lib-voicing-grid`가 같은 열 개수를 따로 관리하다 스코프 하나를 빠뜨리면 어긋났다(§10-9와 같은 유형). `--lib-grid-cols` CSS 커스텀 프로퍼티를 `:root`에 선언하고 두 그리드가 `repeat(var(--lib-grid-cols),1fr)`을 공유하게 해서, 스코프마다 `#view-library { --lib-grid-cols: N }` 한 줄만 바꾸면 둘 다 따라가게 만들었다.

## 12. 훈련소 목록(training.html) 반응형 — 완료

대상: 모바일(기본) / 태블릿 세로(`min-width:560,max-aspect-ratio:1/1`) / 태블릿 가로(`1133~1439w`) / 데스크탑(`1440px+`) / Z Fold 세로힌지 2종(폴드메인 세로힌지, 폴드8 회전형 704×933) / Z Fold 가로힌지 2종(폴드메인 가로힌지, 폴드8 표준형 933×704) / 모바일 가로모드(`min-width:560,max-height:480`). 카드 그리드(`.training-grid`/`.training-card`) 열 수·높이·폰트·아이콘 크기를 스코프별로 조정.

### 가장 어려웠던 부분 — nth-child 특이도가 파일 순서를 이겨버린 버그

폴드메인 세로힌지 스코프에서 만든 "좌3/우3" 배치(`.training-card:nth-child(n){grid-column:...}`)를, 나중에 폴드8 가로힌지(704×933) 스코프를 "4열 그리드"로 바꾸면서 `.training-card{grid-column:auto}`로 리셋했는데도 안 먹혔다. computed style로 `grid-template-columns`는 분명 4열로 나오는데, 실제 배치는 좌3/우3 순서 그대로였다.
- **원인**: `.training-card:nth-child(n)`은 클래스+가상클래스 조합이라 특이도가 (0,2,0)이고, 리셋에 쓴 `.training-card{grid-column:auto}`는 클래스 하나뿐이라 (0,1,0)이다. **파일 순서와 무관하게 특이도가 높은 쪽이 항상 이긴다** — "나중에 나온 규칙이 이긴다"는 이 세션 내내 써온 원칙이 특이도가 다르면 안 통한다는 걸 놓쳤다.
- **찾은 방법**: `grid-template-columns`(내가 리셋한 속성)만 컴퓨티드로 확인하고 "코드는 맞다"고 여러 번 결론 내렸다가, 사용자가 "화면이 거짓말 안 한다, 니 코드를 의심해"라고 강하게 지적한 뒤에야 `grid-column`(안 확인했던 다른 속성)까지 대조해서 발견했다. 이 사건을 계기로 §0(최우선 원칙)을 문서에 새로 추가했다.
- **해결**: 리셋도 똑같이 `.training-card:nth-child(n){grid-column:auto;grid-row:auto}`로 동일한 특이도를 맞춰서 파일 순서가 다시 작동하게 만들었다.
- **교훈**: 스코프 오버라이드가 "이겨야 하는데 안 이긴다"면, 먼저 그 스코프가 건드리는 속성 전부를 나열하고 각각의 소스(어느 스코프의 어떤 선택자가 그 속성을 설정하는지)와 특이도를 대조할 것. 하나의 속성(`grid-template-columns`)이 맞다고 전체가 맞다고 넘겨짚지 말 것.

### 반복적으로 놓친 부분 — 스코프 전수 적용 실패

피크바(`#topbar-currency`) 우측 정렬을 카드 우측 끝에 맞추는 작업을, 요청받은 스코프 하나(태블릿 세로)에만 적용하고 "가로배치도 똑같이 해달라"는 요청을 받고서야 태블릿 가로/데스크탑에 적용했고, 그마저도 사용자가 "폴드메인은 안 됐다"고 재차 지적한 뒤에야 나머지 폴드 4개 스코프까지 전부 찾아서 고쳤다.
- **원인**: `.training-scroll`에 폭 제한(`width:Nvw` 또는 `padding:Nvw`)을 건 스코프가 이 세션에서만 7곳(태블릿 세로/가로, 데스크탑, 폴드메인 세로/가로힌지, 폴드8 세로/가로힌지)이었는데, 매번 "방금 만진 스코프"만 고치고 `grep`으로 `.training-scroll` 전체 목록을 먼저 뽑아보지 않았다.
- **교훈**: 같은 값(정렬 기준점 등)이 여러 스코프에 종속되는 수정을 할 때는, 그 값을 결정하는 상위 속성(여기선 `.training-scroll`의 폭/패딩)을 `grep`으로 전수 조사한 다음 스코프마다 그 상위값에 맞는 하위 공식을 계산해서 한 번에 적용할 것 — 사용자가 스코프 하나씩 알려줄 때까지 기다리지 말 것.

### 캐스케이드 파일 순서 함정 — 이번 세션에도 재발

모바일 가로모드(`min-width:560,max-height:480`)에 `.training-scroll{width:50vw}`를 추가했는데 전혀 안 먹혔다. 원인은 이 스코프를 파일 아주 앞쪽(§2 홈 탭 영역 근처, `.training-scroll` 클래스가 정의되기도 전인 줄)에 넣었기 때문 — `.training-scroll{width:100%}`라는 **미디어쿼리 없는 무조건 규칙**이 그보다 훨씬 뒤(§training 섹션)에 있어서, 같은 특이도의 경우 나중에 나온 무조건 규칙이 항상 이겼다. `.training-scroll` base 규칙 바로 뒤로 옮겨서 해결. §8-1/§11에서 이미 여러 번 겪은 유형인데도 또 걸렸다 — **새 스코프 규칙을 추가할 때는 그 셀렉터의 base 규칙이 파일 어디 있는지부터 확인하고 그 바로 뒤에 놓을 것**을 습관화해야 한다.

### 데스크탑 사이드바 — 서브페이지에 없던 것 추가

`training.html`은 `.app-shell`에 `.top-bar`+`.main-content`만 있고 데스크탑 전용 좌측 사이드바(`<nav class="bottom-nav">`, `grid-area:nav`)가 아예 없어서 데스크탑에서 사이드바 자리가 빈 채로 나왔다. `home.html`의 사이드바는 유저 레벨/닉네임/플랜/XP바를 **홈 탭 프로필 DOM을 미러링**하는 방식이라 이 페이지 것을 그대로 못 가져다 썼다.
- **해결**: 데이터 로딩 로직을 `shared.js`(모든 페이지 공용)로 옮겨서 페이지 독립적으로 만들었다 — `renderProfileXp()`(이미 shared.js에 있던 XP/레벨 계산 함수)에 사이드바 레벨 표시 한 줄 추가, 닉네임/플랜은 새 `loadSidebarUserInfo()`로 최소 fetch만 분리해서 `loadProfileFromDB`(home.js 전용, 홈 탭에 더 많은 걸 채움)가 없는 페이지에서만 실행되도록 가드. 로그아웃은 `confirmLogout()`이 홈 전용 UI(`closeSettings` 등)에 묶여있어서, 서브페이지 로그아웃 버튼은 `home.html?action=logout`으로 이동시키고 홈쪽 URL 파싱에 한 줄만 추가해서 처리.
- **교훈**: 여러 페이지가 공유해야 하는 UI(사이드바)의 데이터 로직은 처음부터 `shared.js`에 두고 "그 페이지에 없으면 그냥 스킵"하도록 짜는 게, 나중에 서브페이지 하나씩 늘려갈 때 각 페이지 전용 스크립트를 뒤지지 않아도 되게 한다.
