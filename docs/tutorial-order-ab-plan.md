# 튜토리얼 스텝 순서 A/B 테스트 — 설계 인계 문서

작성일 2026-08-08 · 대상: 마케팅 세션(실험 설계)
구현 코드는 이미 들어가 있고, **실험 설계·배정·지표 정의가 남았다.**

---

## 1. 무엇을 비교하나

튜토리얼 5스텝의 **순서**를 바꿨을 때 완료 유저의 리텐션이 달라지는지 본다.

| | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|
| **A** (현행) | 코드 에디터 | 코드 사전 | 노트 만들기 | 노트 더 알아보기 | 훈련소 |
| **B** (실험) | 코드 에디터 | 코드 사전 | **훈련소** | 노트 만들기 | 노트 더 알아보기 |

### B를 만든 근거

1. **학습 루프가 붙는다** — 사전(2)에서 코드를 보고 훈련소(3)에서 바로 퀴즈로 확인. A는 둘 사이에 노트 두 스텝이 끼어 있다.
2. **난이도 곡선이 단조증가** — 보기 → 보기 → 고르기(4지선다) → 만들기 → 편집. A는 제일 쉬운 훈련소가 맨 뒤라 곡선이 꺾인다.
3. **day0 이탈 분석과 맞는다** — 소비만 작동하고 제작·학습 수행은 0명이었다. 소비형 스텝을 앞으로 당겨 초반 완주율을 올린다.

### B의 알려진 리스크

튜토리얼 종료 직후의 자연스러운 다음 행동이 달라진다.
A는 "다른 훈련 둘러보기"(반복 방문형)로 끝나고, B는 "내 노트 만들기"(1회성 제작)로 끝난다.
→ B의 마지막 두 구간에서 **출구를 둘 다 열어 두는 문구**로 완화해 두었다("나만의 악보집을 채워 나가면 돼요" + "틈틈이 훈련소도 들러 실력을 쌓아 보세요"). 그래도 이 차이가 리텐션 차이의 교란 요인이 될 수 있으니, 결과 해석 시 순서 효과와 마무리 문구 효과를 분리하지 못한다는 점을 감안해야 한다.

## 2. 이미 구현된 것

### 코드

- **`tutorial-steps.js`**
  - `CHAPTER_DEFS` — 챕터를 key로 정의. key는 순서가 바뀌어도 변하지 않는다.
    `editor` / `library` / `note-create` / `note-edit` / `training`
  - `VARIANT_ORDER = { A: [...], B: [...] }` — **변형 차이는 이 배열뿐이다.**
  - `buildChapters(variant)` — 순서대로 `no`(자리 번호)를 매기고, 완료 문구·다음 버튼 라벨을 자리에서 파생시킨다.
  - 구간(step)의 `variant: 'A' | 'B'` 필드 — 해당 변형에서만 나오는 구간. 필드가 없으면 두 변형 공통.
  - 구간 `title`의 `{S}` 토큰 — 엔진이 `STEP{no}`로 치환. 번호가 문구에 굳어 있지 않다.
- **`tutorial.js`**
  - `_noOf(key)` — 챕터의 현재 자리 번호. 로그에 번호를 하드코딩하지 않기 위해 쓴다.
  - 선물 노트 지급 판정이 `chap.no === 4` → `chap.key === 'note-edit'`로 바뀌었다.
  - `tutorial_step_completed`에 `chapter`(key) 필드가 추가됐다.

### 변형별로 갈리는 문구 (전부 `variant` 필드로 처리됨)

| 위치 | A | B |
|---|---|---|
| 훈련소 도입 1 | 악보를 만들 수 있게 됐지만 / 손이 따라주지 않으면 아쉽겠죠? | 기타 연습, 뭘 어떻게 해야 할지 / 막막할 때가 있죠? |
| 훈련소 도입 2 | 마지막 스텝에선 실력을 키우는 / 훈련소를 둘러볼 거예요! | 이번 스텝에선 기타를 더 재미있고 효율적으로 / 연습할 수 있는 훈련 시스템을 소개드릴게요! |
| 훈련소 종료 | 한 번씩 둘러보며 실력을 쌓아 보세요! / 튜토리얼은 여기까지예요, 수고하셨어요! | 한 번씩 둘러보며 실력을 쌓아 보세요! / 다음 스텝에선 나만의 악보를 만들어 볼게요. |
| 노트심화 종료 | (1구간) 노트를 다루는 법을 전부 익히셨어요! / 마지막 단계에선 실력을 키우는 훈련소로 가볼게요. | (2구간) 노트를 다루는 법을 전부 익히셨어요! / 이제 나만의 악보집을 채워 나가면 돼요.<br>틈틈이 훈련소도 들러 실력을 쌓아 보세요! / 튜토리얼은 여기까지예요, 수고하셨어요! |

A는 앞 스텝(노트=제작)을 전제로 쓸 수 있지만, B의 훈련소 도입은 앞이 에디터·사전(도구·정보)뿐이라 **앞 스텝을 전제하지 않는 문구**로 다시 썼다.

### 총 구간 수

A 132구간 / B 133구간 (B 마무리가 한 박자 더 길다). 길이 차이는 미미하지만 완주 시간 지표에는 잡힌다.

## 3. 아직 없는 것 — 설계 세션이 정해야 할 것

### 3-1. 변형 배정 (가장 먼저)

현재 `window.TUTORIAL_VARIANT`를 채우는 코드가 **없다.** 없으면 전원 A로 떨어져서 지금과 동일하게 동작한다.

제약:

- 이 앱의 **두 번째 실험**이다. 첫 실험에서 쓴 uuid 짝·홀 방식은 직교성이 깨지므로 **쓰면 안 된다.** `hash(user_id + 실험명)` 방식으로 배정한다.
- **배정값은 한 번 정해지면 절대 재계산하지 않는다.** DB `subscriptions.tutorial_step`은 자리 번호(1~5)만 저장하는데, 변형마다 같은 번호가 다른 챕터를 가리킨다. 재배정되면 저장된 진행도의 의미가 통째로 깨진다.
  → 배정값을 유저 레코드에 컬럼으로 **저장**하고, 이후엔 저장값만 읽는다.
- 배정 시점이 튜토리얼 시작보다 늦어질 수 있으므로 `window.TUTORIAL_BUILD_CHAPTERS(variant)`로 다시 만들어 `window.TUTORIAL_CHAPTERS`를 교체하는 경로를 열어 뒀다. 단 **튜토리얼이 이미 진행 중일 때 교체하면 안 된다.**

결정 필요: 배정 컬럼을 `subscriptions`에 붙일지 별도 실험 테이블로 뺄지. (뒤에 실험이 더 붙을 거라면 별도 테이블 쪽이 낫다)

### 3-2. 보상 = 7일 무료 이용권

전제로 깔린 설계: **완료 보상을 미리 공개**하고, 7일 만료 후 리텐션을 A/B로 비교한다.

**구현 완료.** 남은 결정 없음.

- **7일 Pro 체험** — 전체 완주 1회 지급. `complete_tutorial()`이 서버 안에서 `redeem_promo_code()`를 직접 호출한다(유저는 코드를 보지도, 입력하지도 않는다). 기존 promo 시스템을 그대로 태우므로 결제 Pro 이용 중이면 `promo_pending_days`로 적립되고, `subscriptions.plan`은 건드리지 않아 만료 시 자동 원복된다. 만료 기준 시각은 `promo_expires_at`(KST 그날 23:59:59).
- **스텝별 피크상자** — `_tutorial_step_reward(p_step)`: 2 / 3 / 3 / 5 / 5 = 합 18상자(피크 90).
- **보상 예고** — 시작 모달에 "모두 완료하면 7일 Pro 체험!" 배지. `shouldAutoStart()` 경로에서만 열리므로 이미 받은 유저에겐 안 뜬다.
- 만료 임박/종료 안내는 기존 `checkPromoExpiryNotice`(D-3 / D-1 / 종료)가 그대로 처리한다. 추가 구현 불필요.

⚠ **보상은 챕터(key)가 아니라 자리 번호(p_step) 기준으로 준다.** 두 변형의 보상 스케줄이 같아야 순서 효과만 분리된다 — 챕터 기준으로 주면 훈련소가 A는 5번째·B는 3번째라 누적 보상 곡선이 갈려 "순서 때문인지 보상 타이밍 때문인지"를 구분할 수 없다. (이 문서 이전 판에는 key 기반으로 바꿔야 한다고 적혀 있었으나 실험 설계상 반대다.)

선행 조건: `promo_code_system.sql`이 서버에 먼저 적용돼 있어야 한다(`redeem_promo_code` 의존).

### 3-3. 지표 정의

쓸 수 있는 이벤트:

| 이벤트 | 필드 |
|---|---|
| `tutorial_start_modal_viewed` | — |
| `tutorial_started` | `step`(재개 지점) |
| `tutorial_step_completed` | `step`(자리 번호), `chapter`(key) |
| `tutorial_step_continued` | `step` |
| `tutorial_gift_accepted` / `_declined` | `step` |
| `tutorial_skipped` | `step` |

주의:

- **`step`만으로 변형 간 비교를 하면 안 된다.** 같은 3번이 A는 노트 만들기, B는 훈련소다. 챕터 단위 비교는 반드시 `chapter`(key)를 쓴다.
- `tutorial_started`, `tutorial_step_continued`, `tutorial_skipped`, gift 이벤트에는 아직 `chapter`가 없다. 스텝 단위 퍼널을 볼 거면 **이 이벤트들에도 key를 추가해야 한다.** (구현 요청 주면 붙인다)
- 이벤트에 **변형 값이 실려 있지 않다.** 배정 컬럼과 조인해서 붙이든, 이벤트 공통 필드로 넣든 정해야 한다.
- 세션 관련 분석 시 저장된 `session_id`는 2026-06-22 이전 데이터에서 오염돼 있다. sessionization을 직접 해야 한다.
- 유저 단위 분석은 `user_id not null`부터 건다. anon_id 병합 금지.

주 지표 후보: **완료 유저의 7일권 만료 후 리텐션**(D+8 ~ D+14 재방문율). 부 지표: 튜토리얼 완주율, 스텝별 이탈률, 완주 소요 시간, 만료 후 결제 전환.

### 3-4. 표본 크기

주 지표가 "완료 유저" 대상이라 깔때기가 두 번 좁아진다(신규 → 튜토리얼 완주 → 7일 후 관측). 유튜브 공개 코호트 때 하루 372명이 들어온 적이 있으므로, **완주율을 먼저 추정한 뒤 필요 표본과 관측 기간을 역산**해야 한다. 완주율이 낮으면 검정력이 안 나온다.

## 4. 되돌리기

`VARIANT_ORDER.B`를 지우거나 배정 로직을 끄면 전원 A로 떨어진다. 문구는 `variant` 필드로만 갈려 있어 B 전용 구간은 자동으로 빠진다. 코드 롤백 없이 실험만 중단할 수 있다.
