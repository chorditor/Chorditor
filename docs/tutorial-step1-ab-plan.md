# 튜토리얼 step1 A/B 테스트 — 설계 문서 (2차 실험)

작성일 2026-08-10

> 1차 실험(순서 A/B, 에디터를 유지한 채 훈련소 위치만 옮김)은 [tutorial-order-ab-plan.md](tutorial-order-ab-plan.md) 참고.
> 이 문서는 1차 실험 종료 후 도메인 논의로 나온 **2차 가설**(step1 자체를 에디터에서 훈련소로)의 설계 문서다.

---

## 1. 문제정의

배정 대비 "시작하기" 전환은 **44%대**로 레퍼런스(20~35%)보다 오히려 높다. 문제는 그 다음이다 —
시작한 유저 중 **step1(에디터) 완주율이 25%대**로, 레퍼런스("1단계 진입 유저"의 완주율 70~80%)에
비해 매우 낮다.

**step1 완주율을 개선하고, 부가 효과로 최종 완주율까지 끌어올리는 것이 목표다.**

## 2. 가설

**step1을 훈련소로 제시하면 step1 완주율이 크게 개선될 것이다.** 세션 접속 후 실제로 활동한
비율이 훈련 컨텐츠 70% / 에디터 12%로 나타나기 때문(n=3000 이상).

## 3. 근거

### 3-1. 첫 터치 분석 (`supabase/first_touch_feature_analysis.sql`)

퀘스트체인 튜토리얼 배포 전 가입한 유저들이 안내 없이 무엇을 먼저 만졌는지 조회.

| category | users | pct |
|---|---|---|
| training | 2471 | 70.3% |
| library | 615 | 17.5% |
| editor | 423 | 12.0% |
| note | 5 | 0.1% |

- 훈련소/에디터 = **5.8배**. step1을 에디터로 둔 것이 조직적 선호와 정반대.
- 노트는 스스로 거의 안 감(0.1%) → "노트는 저항선"이라는 기존 가설 재확인, 강제 가이드 유지 근거.
- push 유입 배제 시도했으나 `training_page_viewed`엔 애초 push 딥링크 인프라가 없어 organic 신호로 판단.

### 3-2. baseline — 1차 실험 pooled

1차 실험의 구A·구B는 **step1이 둘 다 에디터로 동일**했으므로 합산해 정밀도를 높임.

```
started    = 246 + 242 = 488
step1완료  =  54 +  69 = 123
pooled     = 123/488 = 25.2%  → baseline 25%
```

배정 대비 started 전환도 동일하게 pooled: (246+242)/(548+552) = **44.4%**.
이때 배정 균형(548/552)이 시작 단계(246/242)까지 그대로 유지됐다.

## 4. 지표 정의

| 구분 | 지표 | 기준 |
|---|---|---|
| **Primary** | started 대비 step1 완료율 | baseline 25% → **45% 이상**(+20%p) |
| **Guardrail** | 배정 대비 started 전환율 | baseline 44.4% → **40% 미만이면 위반** |
| **보조** | 최종 완주율(step5 도달), 챕터별 이탈률 | 방향성만 확인 |

**Primary 분모를 started로 잡은 이유**: 모달을 보고 시작할지 말지는 step1 콘텐츠를 보기 전에
결정되므로, 이번 가설("step1 콘텐츠가 완주에 영향을 주는가")과 무관한 잡음이다. 자동모달과
물음표 아이콘 수동 시작 둘 다 started로 합산한다(배정값은 로컬미러로 고정되어 어느 경로로 오든
같은 변형 유지 — `tutorial.js:44,49`).

**Guardrail의 성격 — 정합성 체크**: 위와 같은 이유로 새A/새B 간 이 비율이 갈릴 메커니즘 자체가
없다. 따라서 이건 트레이드오프 감시(1차 실험의 노트 이탈 가드레일)가 아니라, 배정 로직 버그·
모달 노출 이상 등 **실험이 의도치 않게 뭔가를 망가뜨렸는지** 잡는 장치다.

### 4-1. 지표별 분석 대상 인구 (사전 확정 — 사후 변경 금지)

두 지표의 분석 대상을 **다르게** 잡는다. 답하려는 질문이 다르기 때문이다.

| 지표 | 대상 인구 | 판별 | 이유 |
|---|---|---|---|
| **Primary** | 자동모달 + 물음표 아이콘 진입 **둘 다** | `tutorial_started` 전체 | 시작한 시점부터는 조건이 동일 — step1 콘텐츠를 보고 끝까지 하느냐만 잰다 |
| **Guardrail** | **자동모달 경로만** | `tutorial_started` 중 `entry='auto'` | baseline 44.4%가 자동모달 기준이라, 진입 경로가 다른 인구가 섞이면 판정 기준이 어긋난다 |

`entry` 필드(`'auto'`/`'manual'`)는 이 실험을 위해 새로 추가했다. 그전엔 물음표 경로가
`tutorial_started`를 아예 발화하지 않아(`startAt()` 직접 호출) 분모에서 통째로 빠졌다.
**1차 실험 데이터의 started 수치는 전부 자동모달 경로만 집계된 값**이라는 뜻이므로,
baseline 44.4%/25%를 자동모달 기준으로 읽는 것은 정합적이다.

이렇게 나눠도 되는 근거(실무 기준 3조건 전부 충족):

1. **사전 확정** — 이 문서에 실험 시작 전 명시. 결과를 보고 유리한 인구를 고르지 않는다.
2. **각 인구 안에서 랜덤화 유지** — 배정이 `hash(user_id + 실험명)`이라 진입 경로와 완전히 독립.
3. **필터가 변형에 영향받지 않음** — 진입 경로는 step1 콘텐츠를 보기 전에 결정된다.
   (반례: "step1 완료자만 필터링해 뒤 지표를 보는 것"은 필터 자체가 실험 결과에 영향받아
   편향이 생긴다 — post-treatment selection. 여기선 해당 없음.)

## 5. 표본설계

```
baseline p1 = 25%  (§3-2)
MDE         = 20%p (→ p2 = 45%)
α           = 0.01 (양측)
검정력       = 95%

n = (z_α/2 + z_β)² × [p1(1-p1)+p2(1-p2)] / MDE²
  = 17.814 × 0.4350 / 0.04
  = 193.7 → 194명(started, /arm) → 여유 반영 200
```

**MDE=20%p는 계산값이 아니라 판단이다.** 선호도 5.8배 격차(§3-1)를 정성적 신호로 참고했을 뿐,
선호비율을 완주율에 대입하는 공식은 없다(선택확률과 강제완주확률은 다른 종류의 지표). 최종적으론
"이 정도는 돼야 순서를 바꿀 가치가 있다"는 의사결정 임계값이며, 전환 비용이 매우 낮다는 점
(`VARIANT_ORDER` 배열 교체만으로 적용·롤백 가능)이 임계값을 관대하게 잡을 수 있었던 배경이다.

**배정인원 추정치(스케줄링 참고용)**: 194 / 0.444 ≈ 437명/arm → 여유 두고 **500명/arm(총 1000명)**.
실제 정지 신호는 어디까지나 started 카운트다(§6-2). 다만 배정인원을 운영 체크포인트로 삼아도
되는 근거 둘:

1. **구조적**: "시작하기" 결정은 step1 콘텐츠를 보기 전에 일어나므로 변형이 개입할 여지가 없다.
2. **선례**: 1차 실험에서 배정 균형이 시작 단계까지 유지됐다(§3-2).

즉 배정 500/arm 근처에서 started를 확인하는 방식으로 충분하며, 실시간 정밀 감시 인프라는 불필요.

## 6. 실험설계

### 6-1. 변형 정의 — 1차와 이어지지 않게 새로 명명

1차 실험 결과 및 도메인 논의로 **구B(에디터→사전→훈련소→노트→노트)를 채택**했으므로, 이걸
2차 실험의 **새 A(대조군)** 로 삼는다. 1차의 구A(에디터→사전→노트→노트→훈련소)는 폐기.

| | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|
| **새A**(=구B, 대조군) | 에디터 | 사전 | 훈련소 | 노트만들기 | 노트편집 |
| **새B**(신규 가설) | 훈련소 | 사전 | 에디터 | 노트만들기 | 노트편집 |

노트 두 챕터가 항상 4·5번인 이유: 노트 제작은 에디터 스킬을 전제하므로(기술적 의존성),
조직적 선호도와 무관하게 에디터 뒤에 고정.

### 6-2. 배정 방식

- **실험명: `tutorial_step1`** — 1차(`tutorial_order`)와 반드시 달라야 한다. 실험명이 해시에
  섞여야 같은 유저가 또 같은 팔로 몰리지 않는다(직교성, [[ab_test_bucketing]]).
  `get_or_assign_variant`의 화이트리스트(`if p_experiment not in (...)`)에 새 실험명 추가 필요.
- **배정 규칙**: `hash(user_id + 실험명) % 2` → A/B. `experiment_assignments` 테이블에 저장하고
  이후엔 저장값만 읽는다(재계산 금지 — 진행 중 순서가 바뀌면 저장된 `tutorial_step`이 가리키는
  챕터가 통째로 달라진다).
- **배정 시점**: 튜토리얼이 실제로 열리기 직전(`tutorial.js`의 `_ensureVariant()`).
  홈 진입 전원에게 걸지 않는다 — 튜토리얼을 영영 안 여는 유저까지 배정 테이블에 쌓인다.
- **로컬 미러 키에 실험명을 포함한다** — `chorditor_tut_variant__{실험명}`(수정 완료).
  고정 키였을 때는 실험명만 바꿔도 **1차 실험의 배정값이 그대로 읽혀** `_ensureVariant()`가
  서버를 안 부르고 조기 반환했다(`if (_variant || _running) return`). 그러면 새 실험이
  구 배정값으로 돌아가 직교성이 통째로 깨진다 — 조용히 오염돼서 사후 발견도 어려운 종류의 버그다.

### 6-3. 대상 / 제외 조건

**대상: 1.3.3.2 배포 이후 튜토리얼을 처음 시작하는 유저**(기존 유저 + 신규 유저).
반드시 업데이트 이후에 튜토리얼에 접속한 유저여야 한다.

**버전 판별은 별도 장치가 필요 없다** — `EXPERIMENT` 상수가 클라이언트에 하드코딩되므로
구버전은 `'tutorial_order'`로, 1.3.3.2 이상만 `'tutorial_step1'`로 배정을 요청한다.
즉 `experiment='tutorial_step1'` 행은 **정의상 업데이트한 클라에서만** 생성된다 —
배포 시각이나 Play 점진 롤아웃을 신경 쓸 필요가 없다.
교차검증이 필요하면 `analytics_events.app_version`(이벤트마다 기록됨)으로 확인한다.

| 유저 상태 | 포함 | 이유 |
|---|---|---|
| 튜토리얼 모달을 본 적 없음(이탈 중이던 유저 포함) | ✅ | 완전히 깨끗한 대상 |
| 모달은 봤으나 건너뛰었고, step1을 한 번도 시작한 적 없음 | ✅ | 물음표 아이콘으로 다시 들어와 "시작하기"를 눌렀다면 그 시점부터 조건이 동일(§4-1) |
| 튜토리얼 진행 이력 있음(`tutorial_step > 0`) | ❌ | 이미 순서를 경험 — 오염 |

- 진행 이력이 있는 유저는 `shouldAutoStart()`(`tutorial.js`, `step===0 && !skipped`)가
  false라 자동 배정 경로를 타지 않는다. `openTutorialModal()`(물음표 재진입)도
  진행도를 먼저 읽은 뒤 `step===0`일 때만 `_ensureVariant()`를 부르도록 수정 완료.
- 1차 실험(`tutorial_order`) 참여 여부는 제외 조건이 아니다 — 새 실험명으로 해시 재배정되므로
  직교성이 확보되고, 튜토리얼 진행 이력이 있으면 위 규칙에서 이미 걸러진다.

⚠ **1차 실험 구A 배정자 중 진행 중이던 유저**는 배정을 못 받아 새 A(=구B) 순서로 떨어진다.
구A는 3번이 노트, 새A는 3번이 훈련소라 **남은 스텝의 내용이 달라진다.** 구A를 폐기하기로 한
이상 피할 수 없는 부작용이며, 진행 중이던 소수에 한정된다(실험 대상이 아니므로 지표엔 영향 없음).

### 6-4. 정지 규칙(중요 — 1차 실험과 다른 점)

**"배정 인원 수"가 아니라 "started 인원 수"를 직접 감시해서 끊는다.**

1차 실험은 배정 인원(1100명) 기준으로 컷오프를 잡았는데, 정작 중요한 분모(started)의 실측
전환율이 가정과 크게 달라서 표본이 목표에 한참 못 미쳤음(완주자 14명·11명). 이번엔 그 실수를
반복하지 않기 위해, started를 직접 카운트해서 **양쪽 그룹 각 started 200명(§5에서 계산한
194명에 여유 반영) 도달 시 컷오프**로 정한다. 배정인원 추정치는 §5 참고 — 참고치일 뿐 실제
정지 신호가 아니다.

정상 상황(Guardrail 미위반, §4)이면 두 그룹은 거의 같은 시점에 200에 도달한다 — 배정이
50:50 랜덤이고 배정→시작 전환도 변형과 무관해야 하므로(§5 근거 1,2). 만약 한쪽이 유의미하게
늦게 채워진다면 그건 "더 기다려야 하는 상황"이 아니라 **Guardrail 위반 신호**로 다뤄야 한다 —
표본을 강행해서 채우기보다 원인(배정 로직 버그, 모달 노출 이상 등) 규명이 우선이다.

### 6-5. 분석 방법

- **이표본 비율검정(z-test)**, 양측 α=0.01. n=200/arm이면 성공·실패 칸이 모두 충분히 커서
  정규근사 조건을 만족한다(Fisher's exact 불필요).
- 판정은 컷오프(started=200/arm) 도달 후 **1회만**. 중간 관측으로 판정하지 않는다.
- Guardrail도 같은 방식으로 A/B 각각의 배정→started 전환율을 보되, 판정 기준은 유의성이 아니라
  **절대값 40% 미만 여부**다(§4).

### 6-6. 롤백

`VARIANT_ORDER.B`를 지우거나 배정 로직을 끄면 전원 A(대조군 = 현행 순서)로 떨어진다.
변형 전용 문구는 각 구간의 `variant` 필드로만 갈려 있어 자동으로 빠진다 —
**코드 롤백 없이 실험만 중단할 수 있다.**

### 6-7. 선행 작업

**완료됨(2026-08-10, 루트만 — `www`/android 미동기화)**

- ✅ 로컬 미러 키에 실험명 포함(`LS_VARIANT`) — 구 배정값 오염 차단(§6-2)
- ✅ `tutorial_started`에 `entry` 필드 추가(`'auto'`/`'manual'`) 및 **물음표 경로에서도 발화**
  — 그전엔 이 경로가 이벤트를 안 찍어 분모에서 빠졌다(§4-1)

## 7. 유의사항 (1차 실험에서 이어지는 것)

- `step`만으로 비교 금지, `chapter`(key)로 비교할 것 — 새A/새B 모두 step1 위치의 챕터가 다름
  (새A는 editor, 새B는 training).
- 판정은 사전에 정한 컷오프(started=200/arm)에서 1회만. 중간에 들여다보고 임계치나 MDE를
  바꾸지 말 것.
- `session_id` 오염([[bug_session_id_split]]) 있으니 세션 관련 분석 시 직접 sessionization할 것.
- 유저 단위 분석은 `user_id not null`부터. anon_id 병합 금지.
- **"유의하지 않음"을 "차이 없음"으로 읽지 말 것.** 이 설계는 20%p 차이를 잡도록 맞춰져 있어,
  실제 효과가 5~10%p라면 검정력이 부족해 놓친다. 유의하지 않게 나오면 "차이가 없다"가 아니라
  **"이 설계로는 못 본다"**로 기록하고, 더 작은 효과를 볼 가치가 있는지 별도로 판단한다.
- **보조지표는 판정 근거로 쓰지 말 것.** started 200/arm × baseline 25% ≈ step1 완료자 50명/arm,
  거기서 step5까지는 한 자릿수다 — 1차 실험이 실패한 것과 같은 표본 부족 상황이므로 방향성
  참고용으로만 본다.
